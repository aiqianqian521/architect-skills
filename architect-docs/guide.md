# 文档工程与知识管理

> ⚠️ **单 atom 调用硬规则（未经 Router 必读）**：交付必须含四件套——**结论 / 证据（行级）/ 风险分级 / 下一步**。风险分级按 `reference/risk-grading-scheme.md` 量化口径（critical/high/medium/low 触发条件+响应时间）判定，骨架参见 [[architect-router]]#原子风险分级与下一步骨架。不得只给结论不分级、不得只分级不给下一步。

## ADR（架构决策记录）

### 模板
```markdown
# ADR-{序号}: {一句话标题}

## Status
proposed | accepted | deprecated | rejected | superseded by ADR-XXX

## Context
为什么要做这个决策？什么背景？

## Decision
具体决定是什么？

## Alternatives Considered
考虑过哪些方案？为什么没选？

## Consequences
正面影响: ...
负面影响: ...
```

### 什么应该记录 ADR
- 数据库选型（SQLite vs PostgreSQL）
- 文件格式选择（JSONL vs SQLite for events）
- 阈值/常量（fix_confidence=1.0 为什么不是 0.8）
- 重试策略（为什么 3 策略而不是 2 策略）
- 架构模式（为什么端口-适配器）

### 什么不需要 ADR
- 显而易见的决策（用 Python 写 Python 项目）
- 临时的、容易回滚的
- 纯实现细节（变量命名）

## 写给 AI 看的文档（writing-for-agents）

### CLAUDE.md 最佳实践
```markdown
# 项目名 — 一句话定位

## 核心代码入口（表格）
| 模块 | 文件 | 说明 |
|------|------|------|

## 编码约定
- Python 3.11+, 零依赖优先
- 测试基线: 137 passed / 0 failed

## 运行命令（可直接复制执行）
```bash
python orchestrator.py --doctor
```

## 禁止事项
- 禁止 look-ahead bias
- 禁止跳过预过滤
```

### 原则
- **前导词**: 用"铁律"、"禁止"、"强制"而非"应该"、"建议"
- **上下文指针**: 触发条件 + 分支（if X then read Y）
- **信息层级**: 文件内步骤 > 文件内引用 > 外部引用 > 渐进披露
- **单一真相源**: 不重复配置值、不重复文档
- **避免否定**: 写"使用 WAL 模式"而非"不要使用 DELETE 模式"

## 技术调研（search-first）

### 5 步调研流程

**Step 1 — 并行搜索**: 同时在 3 个源搜索候选方案
- PyPI: `pip search <关键词>` 或 pypi.org
- GitHub: `gh search repos <关键词>` 或 github.com/topics
- 专业注册表: MCP registry、npm、技能市场

**Step 2 — 快速筛选**: 按 3 个硬指标初筛（30 秒/候选）
- 最近更新 <1 年
- Star >50 或下载量 >1000/周
- 有 README + 至少 1 个示例

**Step 3 — 并行深研 2-3 个候选**: 对每个进入初筛的候选独立调研
- 读 README、API 文档、快速入门
- 在项目中写最小可行 demo（单文件）
- 记录: 优点、痛点、学习曲线、缺失功能

**Step 4 — 6 维度评估**

| 维度 | 要回答的问题 |
|------|------------|
| 功能 | 是否满足 80% 核心需求？缺失的功能能否绕过？ |
| 维护 | 最近 commit <3 月？Issue 有回复？ |
| 社区 | 文档质量？Stack Overflow 问答数？ |
| 许可 | 是否兼容项目许可？ |
| 依赖 | 会引入多少传递依赖？安全审计通过？ |
| 体积 | 对项目体积增加多少？是否可选依赖？ |

**Step 5 — adopt/extend/build 决策**
- → **adopt**: 直接引用（成熟 + 功能完全匹配 + 零依赖优先）
- → **extend**: 包装一层薄适配器（核心可用，需要统一接口或定制行为）
- → **build**: 自己写（太简单不值得引入 / 太特殊无现成方案 / 依赖过多）

### 调研交付物
```markdown
# 技术调研: <需求名>
## 候选方案
| 候选 | 版本 | Stars | adopt/extend/build | 理由 |
## 推荐方案
方案: <名称> → <决策>
理由: <一句话>
替代方案: <如果推荐被拒，第二选择>
```

## 证据、引用与文档验证

技术文档应区分事实、决策和假设，避免把“看起来合理”写成已验证结论。

| 内容 | 最小证据 |
|------|---------|
| 代码行为 | 文件路径 + 行号 + 可重复命令 |
| 外部事实 | 官方文档/规范 URL + 访问日期 + 版本 |
| 性能结论 | 基准命令、数据集、环境、P50/P95/P99 |
| 安全结论 | 威胁模型、边界条件、验证结果 |
| 架构决策 | ADR 编号、替代方案、可逆性和触发复审条件 |

### 发布前文档门禁

- 链接必须可访问；本地路径必须存在，命令必须能复制执行。
- 示例中的版本、阈值、路径和测试基线不能与代码/CI 矛盾。
- 文档中的每个“必须/禁止”都要能映射到测试、lint、hook 或审查步骤。
- 外部资料失效时保留本地摘要和来源日期，并标记需要复核的段落。
- 重大 API/schema 变更同时更新 Spec、迁移说明、回滚说明和 changelog。

## 常见问题修复指南

### 文档 AI 不可读 → 重写
1. 检查是否有"一句话定位"（第一行就要说清楚是什么）
2. 检查运行命令是否可直接复制执行
3. 检查是否用"强制/禁止"替代了"应该/建议"
4. 参见 [[architect-workflow]] 领域术语表

### 决策遗漏 → 补 ADR
1. 搜索 git log 找到"为什么选了 X 而不是 Y"的讨论
2. 用 ADR 模板记录: Context → Decision → Alternatives → Consequences
3. 记录当时的约束条件（之后约束可能变化）

> **修复验证标准（必填）**：本节任一修复完成后，须给出**可运行验证命令 + 通过条件**或可观测判据；仅"我改了/已调整"不算完成（对照 Router 交付协议第 3 步）。
## cycle-18 实测增补：机器可读引用自证（2026-10-23）

> 来源：cycle-18 A —— 对"文档里会被机器读回的引用"做审计（真值 file:行段：`contract.json` DOC-06）。

**DOC-06 · 文档中的机器可读引用必须有校验器并与单一事实源交叉**：文档里凡是"写下来就会被机器读回"的东西 ——
提交链、`head <hash>`、`N passed / coverage X%`、配置键名（`LOOP_QUOTA_FILE`）—— 都必须有脚本/测试解析
**活文档**并对照单一事实源（git 历史、`docs/baseline.json`），**禁止只靠人工同步**：

- 校验器要 fail-closed：解析不到锚点 = 失败，不允许"找不到就跳过"。
- 校验器自身要有负例自证（改坏文档必须报错），并且要有覆盖度自证（断言的条目数 >= 阈值，防止空解析全绿）。
- 反例（loop 实证）：cycle-17 之前 `docs/baseline.json` 的 passed/coverage 从不对照实测运行（cycle-17 修，单向棘轮）；
  cycle-18 发现唤醒指针提交链把 cycle-16 A 记成 cycle-17 的哈希、真哈希全文缺失（cycle-18 修，
  `tests/test_wake_pointer_chain.py`）。

写作启示：**凡是"记录"，要么有校验器，要么迟早会在某个 agent 的推理链里变成事实。**

## DOC-07 · 正文哈希引用必须可解析（幽灵哈希家族）

> 来源：cycle-20 A —— loop-dev-next 三仓交叉取证。

**DOC-07 · 文档正文里的提交哈希必须能被机器解析**：与 DOC-06 同族；DOC-06 盯的是「声明形态」（提交链、`head <hash>`、基线数字、配置键名），DOC-07 盯的是**正文散文里的哈希**——它同样会被下一个 agent 当作事实。反例：loop cycle-20 全仓扫描命中 3 个三仓都解析不出的幽灵哈希（❌错记 `11588a1` / `a67594c` / `8cf9d4c`）。

- 逐个反引号哈希、逐条箭头链都要解析到**已知仓**；解析不出 = 失败（fail-closed）。
- 只扫反引号哈希与箭头链（日期串会误匹配 hex 模式，全裸扫不可接受）。
- 引用缺陷值必须同行标记（❌错记 / phantom）。
- 校验器要有负例自证：放一条解析不出的哈希必须报错；删掉必须恢复 0 违例。

## DOC-08 — 文档正文里「裸写」的提交哈希也必须有校验器保证可解析（同行 git 上下文门控 + 外部源仓 pin 登记）

> 触发：loop cycle-21 A（承接 DOC-07）。DOC-07 覆盖了反引号哈希与 `A→B→C` 箭头链，但**裸写（无反引号）的提交哈希**仍是盲区。

**DOC-08 — 裸写的提交哈希也有校验器保证可解析**，禁止只靠「人写的时候看清了」：① 裸哈希仅当同行已含可解析提交引用时才计入；② 每个裸哈希须在已知仓真实存在；③ 外部源仓 pin 须登记 checkout 后解析；④ 带摘要标签的行跳过；⑤ 纯数字 token 排除（日期同现会误报）。反例（loop cycle-21）：GRAND-LOOP 的唤醒指针路径行与 status 的提交列，共 **79 个唯一裸 token** 从未被校验——任何照链取证的 agent 都可能把其中写错的哈希当成事实传递。

## DOC-09 — 文档里的提交引用校验必须写清「扫哪些语料」，跨语料的不可解析值必须分类取证

> 触发：loop cycle-22 A（承接 DOC-08）。

**DOC-09 — 扫描边界与不可解析值分类必须写进文档**：一个「哈希必须可解析」的校验器，一旦指向本仓之外的语料，就必须同时给出两件事——

- **语料边界**：扫哪些仓、哪些扩展名算账本；机器可读契约 JSON 里的规则文案、历史报告里的数据集指纹都不算「提交声明」。
- **分类规则**：不可解析值分类取证（数据指纹 / 运行时对象 id / 被 amend 掉的中转提交 / 外部仓基线 / 守卫自身示例），**默认仍是幽灵**；分类器只服务取证报告，不接入门禁。

反例（loop cycle-22）：同一套规则指向 legacy loop-dev（2300 篇）+ architect-skills（86 篇）得到 32 处 finding、0 处幽灵 —— 直接当门禁跑会把 32 个合法值全报成假哈希。**第 7 例同族缺陷**：指南曾把守卫示例 token（defaced / effaced / abc123d）用代码跨度逐字复刻，等于把文档本身变成守卫的违规样本；已改为普通文字。

## DOC-10 — 交付的验证器/取证工具本身必须被文档写明「由谁断言」

> 起因：loop cycle-23 A。文档/交接把一个校验器或取证工具当作「已交付的保证」，但没有任何一条写明它的判定由哪条测试直接断言。

**DOC-10 是「验证器必须被验证」在文档侧的落点**：一个工具的判定只要写成 exit code 或手写登记表，文档就必须写明它的判定被哪条测试直接断言，而不是把无人执行的约定当成保证。

- **exit code 是断言**：必须写明「未解释幽灵 → exit 1、全部可解释 → exit 0」两条路径都被测试驱动，禁止只写「发现幽灵返回 1」。
- **登记表不可静默腐烂**：手写登记（如不可解析值登记）必须写明它的接收凭证由测试持续校验，条目一旦开始可解析即为陈旧，必须 FAIL。
- **单测不得依赖环境**：必须写明单测只扫合成语料、不触碰本机兄弟仓。
- **覆盖 ≠ 正确**：0 覆盖、exit code 无人断言的脚本，其判决只是一条未验证的声明。

**反例（loop cycle-23 A）**：cycle-22 交付的 `scripts/audit_cross_repo_ledger.py` 是分类器唯一调用方，此前 0 覆盖、exit code 从未被跑过；补 3 例后 27→30、全量 1615→1618 passed。第 8 例同族缺陷：**交付的验证器本身未被验证**。

## DOC-11 — 文档一致性校验的作用域必须写明并覆盖「入口文档」

> 起因：loop cycle-24 A。文档声明「当前态文档与基线一致」，但手写校验清单漏掉了入口文档（wake pointer）。

- 必须写明校验清单覆盖哪些文件，且**入口文档（第一个被读取的，如 wake pointer）必须在内**；
- 手写清单可静默缩水，必须被测试断言（入口文档在清单内 + 改坏入口文档必须 FAIL）；
- 边界要写清：历史 / 快照 / 设计记录类文档不纳入是刻意的；入口文档漏掉不是刻意的。

**反例（loop cycle-24 A）**：`docs_baseline` 漏掉 `docs/flow/GRAND-LOOP.md`，把它的基线数字改成 `9999 passed` / `55.55%` 后校验器仍 OK。

## DOC-12 — 『最新状态 / 下一步』的标号必须被机器校验

> 起因：loop cycle-25 A。文档用标号（§13.N）指向『下一目标』，标号与注册表都是手写的，此前无校验。

- 必须写明该标号指向哪份注册表，以及『标号 = 注册表最新号 + 注册表连续无重复』这一校验；
- 手写标号会随每轮追加漂移，必须被测试断言，禁止只靠人工手动 +1；
- fail-closed：指针缺失 / 注册表为空即失败。

**反例（loop cycle-25 A）**：`docs/flow/GRAND-LOOP.md` 的 §13.N 指针与状态注册表最新小节此前无校验，改成过期编号无人发现。

## DOC-13 — 历史数字必须带锚点：当前态唯一等于基线，历史值必须标注

> 起因：loop cycle-26 A。文档写下「当时实测」的数字是正常的，但**不标注**就会被当成现值。

- 必须写明该文档的一致性校验口径：**当前态数字唯一等于基线**，历史数字必须带可识别锚点（日期 20xx / 轮次号 cycle-N / 「历史」）；
- 锚点作用域是**数字所在的块**（bullet / 段落 / 标题），不是整篇文档——「文档某处写过日期」不能洗白一条并排的旧数字；
- 步进计数（如 `1/1 passed`）不是基线数字，不在口径内。

**反例（loop cycle-26 A）**：`docs/loop-dev-AS-BUILT.md:169` 的 `758 passed` 与 `docs/loop-dev-ROADMAP.md` §4 的 `734/745/755/758` 无任何锚点，文档一致性校验一路 OK。

## DOC-14 — 引用的识别口径必须统一、来源必须可解析、且不得误报

> 起因：loop cycle-27 A。引用写法（全 / 半角括号、哈希长度）随作者变化，识别口径一旦窄于现实，引用就被漏扫——读者拿到的是一份「看似干净、实则未审」的文档。

- 识别口径必须与代码守卫一致：长度 7..40、全角与半角括号、括号前可有空白；
- 每条被引用的哈希必须能在其**真实来源仓**（本仓 / 历史仓 / 姊妹仓 / 外部源 pin）解析；
- 引用旁的轮次标注若写了 cycle-N 必须与提交信息一致：不写不罚，写了不一致即 FAIL；
- **假阴性（漏扫）与假阳性（把合法跨仓引用报成幽灵）都算违规**，两者都要有自证用例。

**反例（loop cycle-27 A）**：`docs/flow/2026-09-05-grand-loop-task.md` 的 `64de89b`（cycle-1）用全角括号写作 → 所有扫描器都看不见；该哈希只在历史仓 loop-dev 中 → 口径一放宽就会因只看本仓而被报成幽灵。

## DOC-15 — 护栏的行为契约必须写清：见证、出口、渲染口径、已知边界

> 起因：loop cycle-28/29。文档里一句「有纵深防御」不等于读者知道它拦什么、放什么、拒了怎么说。

- 宣称存在一道护栏（权限矩阵 / 风险评分 / 沙箱 / 门禁）时，必须写明每条规则**能命中什么**（见证命令）与**命中后的出口**（allow / deny / escalate）；escalate 未接线时等同 deny 必须写明。
- 必须写明拒绝信息的**渲染口径**：策略拒绝与路径越界是两种原因，混写会让下游 agent 拿着错原因做归因（D-G2）。
- 护栏的**已知边界**（词边界 / 字母表 / 空格切分导致的假阳性或假阴性）必须显式登记——边界是决定，不是意外。
- 结论必须可被独立驱动复核：给出命令 + 期望出口。

**反例（loop cycle-28/29）**：`docs/flow/2026-09-05-grand-loop-status.md` 的 F9 探针把锁路径写成 `<repo>/loop-engine/.loop.lock`，
实现却是 `<runtime.root>/.loop.lock`，于是「无残留锁」的不变量成了**空断言**（D-S1）；同族：`arg_rules` 里 `curl |` 无见证命令、`escalate` 出口没有文档语义。


## DOC-16 — 文档 / 报告的证据引用必须可落地：没有快照就显式自引

> 起因：loop cycle-30 A。文档里一句 `data/rounds.json` 如果指向不存在的目录，就是交给读者一张假地图。

- 每条 `file:line:` 必须在读者可解析的锚点下存在：相对产物目录、仓根，或绝对的路径；三选一，都必须真实。
- 无同目录数据快照时必须**显式标注**（自引产物本体），不得声称 `data/<x>.json`。
- 文档若宣称「报告自带校验」，必须写明该校验校验的是**存在性**而非标签——否则那层自校验是障眼法
  （与 DOC-10「验证器的判定由哪条测试断言」同族）。
- 把读者送到不存在的路径 = 伪造证据指针（D-S1 家族：断言了永不存在的路径）。

**反例（loop cycle-30 A）**：带日期客户报告宣称 `data/*.json` 与 `+ data/`，实际从不产出该目录；报告内
自校验只匹配标签，对断链一路 OK。修：自校验加存在性 + 生产者改引真实归档（或自引）。

## DOC-17 — 机械记录的书写形态必须与校验器同宽；看不见的形态要显式登记

> 起因：loop cycle-31 A。文档里一条用全角括号写的链条目，对只认半角的校验器等于不存在——
> 文档「看起来干净」，其实那一行从未被审。

- **形态必须在校验器的形态集内**：写提交链 / 哈希引用 / 唤醒指针时使用的括号、前缀、分隔符要落在
  校验器识别的集合里；否则该记录不被扫描（假阴性：看似干净、实则未审）。
- **不被覆盖的形态要写成决定**：写清「哪种写法不算机器声明、为什么」，并配负例。例：哈希旁的
  「逗号 / 破折号 + cycle-N」不算声明——扩宽会把散文「截至 cycle-N」读成声明而误报。
- **口径共用同一常量**：长度 7..40、全 / 半角括号、括号前空白这些写法约定，文档口径要与代码校验器一致
  （与 DOC-14「识别口径必须与代码守卫一致」同源，本轮把范围从字母表扩到全部定点）。
- **唯一性要写明**：唤醒指针这类记录只有一处；多写一处会让读者拿到两个「当前值」。

**反例（loop cycle-31 A）**：全角括号的链条目对 `ENTRY_RE` 不可见（同一条用半角写就能被审）；
不写出来就无法发现文档已经漂移成一个「从未被校验」的形态。

## DOC-18 · 文档里的豁免标注必须与被豁免的内容同界

> 起因：loop cycle-32 A。文档若用一个「标记 / 忽略」把整行标成免检，同行的坏哈希就会被
> 读者 agent 当成「已登记」——豁免的边界宽于内容，就是记录了错误事实。

- **同界**：一个标注只豁免它标注的那个引用，不得整行 / 跨单元格外溢。
- **标注词是写作约定**：符号或全大写短语，不得用可能出现在正文 / 代码里的普通词；
  否则一句提到函数名的散文就豁免整行。
- **远距离豁免要登记**：表格行这类无法紧邻的豁免，必须显式登记并写明理由，登记不得静默腐坏。
- **自证**：把标注词换成普通词、或把标记放远超过阈值，校验必须变红。

**反例（loop cycle-32 A）**：`_is_defect_line` 整行豁免且 `phantom` 是标记 ⇒ 注释里提到函数名
即豁免整行。

## DOC-19 · 裸哈希的提交引用必须落在校验器的触发范围内

> 起因：loop cycle-33 A。裸哈希是否被校验，取决于「关键词是否紧邻」；若依赖「同行
> 还有别的引用」，唯一的声明就永远不会被审。

- **让关键词紧邻 token**：把提交引用写成「commit <hash>」「HEAD <hash>」这类紧邻形态，
  它才会被校验器的触发条件覆盖。
- **不要依赖共现**：不要指望「同一行还有别的可解析引用」来让校验生效——那只覆盖了碰巧的
  情形，唯一的声明仍会漏掉。
- **放宽要有实测**：校验器侧按紧邻性放宽时，必须用语料实测证明零误报（全 hex 英文词 / 指纹
  / 运行 id 不得被误伤）。
- **自证**：写一行仅含「commit <坏哈希>」的文档，校验必须变红。

**反例（loop cycle-33 A）**：「fixed in commit <坏哈希>」孤立一行此前从不报红。

## DOC-20 · 免检标签的作用域不得大于它豁免的对象

> 起因：loop cycle-34 A。用摘要标签解释「这不是提交引用」时，说明只覆盖它标注的那个值；
> 若让整行都免检，同一行里的坏哈希会被读者 agent 当成「已解释」。

- **只作用于被标注的那个值**：标签（md5= / sha256: / checksum:）只解释它**紧邻标注**的值；
  同行的其它裸哈希仍需被校验，或另行说明。
- **不得整行免检**：不要用「这一行有摘要标签」来默认整行都已解释——那是把豁免的边界写得比对象宽。
- **分界线写清并配负例**：标签须紧邻其值；仅「靠近」标签的 token 不受保护。
- **自证**：把「commit <坏哈希>」与「md5=<摘要>」写在同一行，校验必须变红；而仅写「md5=<摘要>」必须静默。

**反例（loop cycle-34 A）**：一行带 md5= 标签就整行跳过裸哈希扫描 ⇒ 同行的真提交声明从不报红。

## DOC-21 · 受控声明必须附可核对证据，且规模完整

> 起因：loop cycle-35 A。文档若宣称「已受门控 / 已覆盖」，就必须能被核对；
> 只列前几条、或凭「名字里出现了门」下结论，都会让读者把「没人报错」当成「没有问题」。

- **附可核对证据**：指向登记表 / 断言 / 检查产物，而不是散文推断。
- **例外逐条写明并给出理由**：哪些站点在域外、为什么；例外表要能被检查（仍生效、不静默腐坏）。
- **规模完整**：写「已排除 N 处」时不得只列前几条——截断会让人低估问题规模。
- **写清覆盖范围（扫描域）**：哪些文件在域内、哪些不在；否则「无人报错」只是「没人看」。

**反例（loop cycle-35 A）**：不变量 1 的报告被截断且按名字豁免，文档据此宣称「单点出口」，实为 5 处绕过。

## DOC-22 · 可选依赖必须写明缺省即拒绝

> 触发 loop cycle-36 A：文档把「可选 gate」写成兼容性便利，读者就会以为缺省仍然安全；
> 缺省语义必须写成 fail-closed。

- **缺省即拒绝**：安全关键参数未注入时必须写明会拒绝执行，而不是「兼容地继续」。
- **降级等于决定**：文档若承认存在降级，必须逐条写出理由与作用对象，且该登记可被检查（失效即报警）。
- **不得用「可选」掩盖「忘记注入」**：必须说明生产路径在哪里注入 gate。
- **反例（loop cycle-36 A）**：适配器的 exec_gate=None 回退被描述成兼容性便利，实际是静默裸跑。

**触发 loop cycle-36 A：**文档声明无门即无 spawn，并写明生产组合根（orchestrator / BacktestRunner / evolution loader）在哪里注入 gate。

## DOC-23 · 声称「已强制 / 已接入」必须写清信任边界与生效前提

> 触发 loop cycle-37 A：文档把本地 pre-commit 门禁写成 fail-closed，
> 但读者据此以为「无法绕过」。

- **写清信任边界**：强制点在谁的权限之外执行？被约束方能否自行关闭？能自行关闭的不算强制。
- **写清生效前提**：哪项开关被固定、配置如何到达执行点；只设不导出、被全局配置覆盖都是「没生效」。
- **「已安装」≠「会执行」**：必须有端到端自证（用被约束方的真实动作触发），或明确标注「未验证」。
- **未覆盖范围逐条列出**：例如「未接入 hosted CI，只交付 pre-receive 与安装器」。
- **反例（loop cycle-37 A）**：本地门禁被描述成 fail-closed，实际 --no-verify / 全局 core.hooksPath 即可绕过。

**触发 loop cycle-37 A：**文档写明信任边界 = 接收主机、生效前提 = core.hooksPath 已钉住 + 配置已导出，并附真实 push 自证。

## DOC-24 · 代理指标不得写成语义指标，证据必须写明生产者与作用域

> 触发 loop cycle-38 A：文档里的 RPO 是「行数代理」，读者却容易读成「可恢复到某时刻」。

- **代理必须写成代理**：行数 / 计数 / 哈希是代理指标；「可恢复到某时刻」「不丢数据」只有在存在
  真实时间点 / 业务单元证据时才可写。
- **写明生产者与原子性口径**：证据由谁产生、是否与业务写入同一事务、应用能否绕过。
- **写明历史回填口径**：历史行是否被回填、口径是什么（恰好一次 / 可重放），不得暗示历史行也有真实提交时间。
- **写明作用域**：这是**隔离副本上的演练**还是**生产实测** —— 演练不得当作生产承诺。
- **未覆盖范围逐条列出**：例如「尚未在生产停写窗口实测」「未接入托管 CI」。
- **反例（loop cycle-38 A）**：MIGRATION-RECOVERY 的 RPO 是行数代理；修：写明 `mode=sentinel_timestamp`
  / `verified=true` 及其演练作用域，并把「尚未在生产停写窗口实测」列为已知局限。

**触发 loop cycle-38 A**：迁移恢复文档区分「演练实测（隔离副本）」与「生产 RPO」，并写明哨兵的生产者、原子性与回填口径。

## DOC-25 · 门禁 / 报告的输出必须与判定同源

> 触发 loop cycle-39 A：门禁判定 `measured + 0.15 >= recorded`，通过行却打印 `coverage 79.35% >= 79.47%` —— 一个字面为假的不等式。

- **输出即文档**：门禁 / 校验器 / 报告打印的比较与阈值同样是「文档」，读者会把它当事实。
- **与判定同源**：判定判 `measured < floor`，通过行就必须打印 `measured >= floor`，`floor` 由判定所用的同一函数 / 表达式算出，不得手工复述 recorded 值。
- **容差必须显性**：判定含 slack / tolerance 时，消息必须给出**实际生效的下界**与容差，不得打印 `measured >= recorded` 这种字面为假的不等式。
- **失败行同口径**：给出 `< floor`，而不是只给 recorded。
- **钉一条测试**：构造「刚好落在容差内」的通过用例，断言打印的比较为真、且 `recorded - floor == slack`。
- **反例（loop cycle-39 A）**：`scripts/run_gate.py`；修：抽出 `coverage_floor(recorded) = recorded - tolerance`，判定 `measured < floor`，通过行打印 `coverage X% >= floor Y% [recorded Z%, slack S%]`。

**触发 loop cycle-39 A**：门禁通过行给出实际生效的下界（floor）与容差；判定与消息同一表达式互为取反。

## DOC-26 · 登记的基线必须可复现：偶然读数不是事实

> 触发 loop cycle-40 A/A2：`docs/baseline.json` 登记 79.48%，而干净克隆首跑是 79.47%；
> 同一命令在本机两次运行也会摆动 —— 当时的登记值依赖机器残留状态与线程时序。

- **基线 = 可复现的观测**：登记的通过数 / 覆盖率必须能在干净克隆上逐字重现，且同一命令连续两次一致；“文档说的 == 实测的”以“实测可复现”为前提。
- **先消除耦合再登记**：受机器残留（运行态目录 / 草稿 / 缓存）或时序影响的数字，必须先修测试，不得把一个偶然读数写成基线。
- **无法消除就写明**：波动幅度、原因、由哪条容差吸收，并说明登记值取在可复现的一侧。
- **容差不是遮羞布**：不得用“落在容差内”掩盖“同一命令两次结果不同”。
- **变更要留痕**：同轮给出新旧值与复现命令；历史值必须带锚点（日期 / cycle-N）。
- **反例（loop cycle-40 A/A2）**：登记 79.48% 对干净克隆 79.47% 且本机两次摆动；修：先消除耦合（会话级清理 / 可注入 seam / 单线程驱动分支），再把登记值取在干净克隆可复现的 79.49%。

**触发 loop cycle-40 A/A2**：文档写明基线的可复现口径（干净克隆 + 连续两次一致），波动必须登记并说明容差。
