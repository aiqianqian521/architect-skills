# 文档工程与知识管理

> ⚠️ **单 atom 调用硬规则（未经 Router 必读）**：交付必须含四件套——**结论 / 证据（行级）/ 风险分级 / 下一步**。风险分级按 `reference/risk-grading-scheme.md` 量化口径（critical/high/medium/low 触发条件+响应时间）判定，骨架参见 [[architect-router]]#原子风险分级与下一步骨架。不得只给结论不分级、不得只分级不给下一步。

## ADR（架构决策记录）

### 模板
```markdown
# ADR-{序号}: {一句话标题}

## Status
proposed | accepted | deprecated | rejected | superseded by ADR-XXX

## Context
为什么要做这个决策？什么背景？

## Decision
具体决定是什么？

## Alternatives Considered
考虑过哪些方案？为什么没选？

## Consequences
正面影响: ...
负面影响: ...
```

### 什么应该记录 ADR
- 数据库选型（SQLite vs PostgreSQL）
- 文件格式选择（JSONL vs SQLite for events）
- 阈值/常量（fix_confidence=1.0 为什么不是 0.8）
- 重试策略（为什么 3 策略而不是 2 策略）
- 架构模式（为什么端口-适配器）

### 什么不需要 ADR
- 显而易见的决策（用 Python 写 Python 项目）
- 临时的、容易回滚的
- 纯实现细节（变量命名）

## 写给 AI 看的文档（writing-for-agents）

### CLAUDE.md 最佳实践
```markdown
# 项目名 — 一句话定位

## 核心代码入口（表格）
| 模块 | 文件 | 说明 |
|------|------|------|

## 编码约定
- Python 3.11+, 零依赖优先
- 测试基线: 137 passed / 0 failed

## 运行命令（可直接复制执行）
```bash
python orchestrator.py --doctor
```

## 禁止事项
- 禁止 look-ahead bias
- 禁止跳过预过滤
```

### 原则
- **前导词**: 用"铁律"、"禁止"、"强制"而非"应该"、"建议"
- **上下文指针**: 触发条件 + 分支（if X then read Y）
- **信息层级**: 文件内步骤 > 文件内引用 > 外部引用 > 渐进披露
- **单一真相源**: 不重复配置值、不重复文档
- **避免否定**: 写"使用 WAL 模式"而非"不要使用 DELETE 模式"

## 技术调研（search-first）

### 5 步调研流程

**Step 1 — 并行搜索**: 同时在 3 个源搜索候选方案
- PyPI: `pip search <关键词>` 或 pypi.org
- GitHub: `gh search repos <关键词>` 或 github.com/topics
- 专业注册表: MCP registry、npm、技能市场

**Step 2 — 快速筛选**: 按 3 个硬指标初筛（30 秒/候选）
- 最近更新 <1 年
- Star >50 或下载量 >1000/周
- 有 README + 至少 1 个示例

**Step 3 — 并行深研 2-3 个候选**: 对每个进入初筛的候选独立调研
- 读 README、API 文档、快速入门
- 在项目中写最小可行 demo（单文件）
- 记录: 优点、痛点、学习曲线、缺失功能

**Step 4 — 6 维度评估**

| 维度 | 要回答的问题 |
|------|------------|
| 功能 | 是否满足 80% 核心需求？缺失的功能能否绕过？ |
| 维护 | 最近 commit <3 月？Issue 有回复？ |
| 社区 | 文档质量？Stack Overflow 问答数？ |
| 许可 | 是否兼容项目许可？ |
| 依赖 | 会引入多少传递依赖？安全审计通过？ |
| 体积 | 对项目体积增加多少？是否可选依赖？ |

**Step 5 — adopt/extend/build 决策**
- → **adopt**: 直接引用（成熟 + 功能完全匹配 + 零依赖优先）
- → **extend**: 包装一层薄适配器（核心可用，需要统一接口或定制行为）
- → **build**: 自己写（太简单不值得引入 / 太特殊无现成方案 / 依赖过多）

### 调研交付物
```markdown
# 技术调研: <需求名>
## 候选方案
| 候选 | 版本 | Stars | adopt/extend/build | 理由 |
## 推荐方案
方案: <名称> → <决策>
理由: <一句话>
替代方案: <如果推荐被拒，第二选择>
```

## 证据、引用与文档验证

技术文档应区分事实、决策和假设，避免把“看起来合理”写成已验证结论。

| 内容 | 最小证据 |
|------|---------|
| 代码行为 | 文件路径 + 行号 + 可重复命令 |
| 外部事实 | 官方文档/规范 URL + 访问日期 + 版本 |
| 性能结论 | 基准命令、数据集、环境、P50/P95/P99 |
| 安全结论 | 威胁模型、边界条件、验证结果 |
| 架构决策 | ADR 编号、替代方案、可逆性和触发复审条件 |

### 发布前文档门禁

- 链接必须可访问；本地路径必须存在，命令必须能复制执行。
- 示例中的版本、阈值、路径和测试基线不能与代码/CI 矛盾。
- 文档中的每个“必须/禁止”都要能映射到测试、lint、hook 或审查步骤。
- 外部资料失效时保留本地摘要和来源日期，并标记需要复核的段落。
- 重大 API/schema 变更同时更新 Spec、迁移说明、回滚说明和 changelog。

## 检查清单

```
[ ] 每个重要技术决策是否有 ADR？ → 没有: 用 ADR 模板补记录（见上方模板）
[ ] CLAUDE.md 是否有一句话定位 + 运行命令 + 禁止事项？ → 补全: 用"写给 AI 看的文档"原则重写
[ ] 文档是否用前导词（"强制"、"禁止"）而非弱建议？ → 扫描全文，将"应该"替换为"必须"/"禁止"
[ ] 是否先搜索了已有方案再自己写代码？ → 未搜索: 执行上方 5 步调研流程

## 常见问题修复指南

### 文档 AI 不可读 → 重写
1. 检查是否有"一句话定位"（第一行就要说清楚是什么）
2. 检查运行命令是否可直接复制执行
3. 检查是否用"强制/禁止"替代了"应该/建议"
4. 参见 [[architect-workflow]] 领域术语表

### 决策遗漏 → 补 ADR
1. 搜索 git log 找到"为什么选了 X 而不是 Y"的讨论
2. 用 ADR 模板记录: Context → Decision → Alternatives → Consequences
3. 记录当时的约束条件（之后约束可能变化）

> **修复验证标准（必填）**：本节任一修复完成后，须给出**可运行验证命令 + 通过条件**或可观测判据；仅"我改了/已调整"不算完成（对照 Router 交付协议第 3 步）。
## cycle-18 实测增补：机器可读引用自证（2026-10-23）

> 来源：cycle-18 A —— 对"文档里会被机器读回的引用"做审计（真值 file:行段：`contract.json` DOC-06）。

**DOC-06 · 文档中的机器可读引用必须有校验器并与单一事实源交叉**：文档里凡是"写下来就会被机器读回"的东西 ——
提交链、`head <hash>`、`N passed / coverage X%`、配置键名（`LOOP_QUOTA_FILE`）—— 都必须有脚本/测试解析
**活文档**并对照单一事实源（git 历史、`docs/baseline.json`），**禁止只靠人工同步**：

- 校验器要 fail-closed：解析不到锚点 = 失败，不允许"找不到就跳过"。
- 校验器自身要有负例自证（改坏文档必须报错），并且要有覆盖度自证（断言的条目数 >= 阈值，防止空解析全绿）。
- 反例（loop 实证）：cycle-17 之前 `docs/baseline.json` 的 passed/coverage 从不对照实测运行（cycle-17 修，单向棘轮）；
  cycle-18 发现唤醒指针提交链把 cycle-16 A 记成 cycle-17 的哈希、真哈希全文缺失（cycle-18 修，
  `tests/test_wake_pointer_chain.py`）。

写作启示：**凡是"记录"，要么有校验器，要么迟早会在某个 agent 的推理链里变成事实。**

## DOC-07 · 正文哈希引用必须可解析（幽灵哈希家族）

> 来源：cycle-20 A —— loop-dev-next 三仓交叉取证。

**DOC-07 · 文档正文里的提交哈希必须能被机器解析**：与 DOC-06 同族；DOC-06 盯的是「声明形态」（提交链、`head <hash>`、基线数字、配置键名），DOC-07 盯的是**正文散文里的哈希**——它同样会被下一个 agent 当作事实。反例：loop cycle-20 全仓扫描命中 3 个三仓都解析不出的幽灵哈希（❌错记 `11588a1` / `a67594c` / `8cf9d4c`）。

- 逐个反引号哈希、逐条箭头链都要解析到**已知仓**；解析不出 = 失败（fail-closed）。
- 只扫反引号哈希与箭头链（日期串会误匹配 hex 模式，全裸扫不可接受）。
- 引用缺陷值必须同行标记（❌错记 / phantom）。
- 校验器要有负例自证：放一条解析不出的哈希必须报错；删掉必须恢复 0 违例。

## DOC-08 — 文档正文里「裸写」的提交哈希也必须有校验器保证可解析（同行 git 上下文门控 + 外部源仓 pin 登记）

> 触发：loop cycle-21 A（承接 DOC-07）。DOC-07 覆盖了反引号哈希与 `A→B→C` 箭头链，但**裸写（无反引号）的提交哈希**仍是盲区。

**DOC-08 — 裸写的提交哈希也有校验器保证可解析**，禁止只靠「人写的时候看清了」：① 裸哈希仅当同行已含可解析提交引用时才计入；② 每个裸哈希须在已知仓真实存在；③ 外部源仓 pin 须登记 checkout 后解析；④ 带摘要标签的行跳过；⑤ 纯数字 token 排除（日期同现会误报）。反例（loop cycle-21）：GRAND-LOOP 的唤醒指针路径行与 status 的提交列，共 **79 个唯一裸 token** 从未被校验——任何照链取证的 agent 都可能把其中写错的哈希当成事实传递。

## DOC-09 — 文档里的提交引用校验必须写清「扫哪些语料」，跨语料的不可解析值必须分类取证

> 触发：loop cycle-22 A（承接 DOC-08）。

**DOC-09 — 扫描边界与不可解析值分类必须写进文档**：一个「哈希必须可解析」的校验器，一旦指向本仓之外的语料，就必须同时给出两件事——

- **语料边界**：扫哪些仓、哪些扩展名算账本；机器可读契约 JSON 里的规则文案、历史报告里的数据集指纹都不算「提交声明」。
- **分类规则**：不可解析值分类取证（数据指纹 / 运行时对象 id / 被 amend 掉的中转提交 / 外部仓基线 / 守卫自身示例），**默认仍是幽灵**；分类器只服务取证报告，不接入门禁。

反例（loop cycle-22）：同一套规则指向 legacy loop-dev（2300 篇）+ architect-skills（86 篇）得到 32 处 finding、0 处幽灵 —— 直接当门禁跑会把 32 个合法值全报成假哈希。**第 7 例同族缺陷**：指南曾把守卫示例 token（defaced / effaced / abc123d）用代码跨度逐字复刻，等于把文档本身变成守卫的违规样本；已改为普通文字。

## DOC-10 — 交付的验证器/取证工具本身必须被文档写明「由谁断言」

> 起因：loop cycle-23 A。文档/交接把一个校验器或取证工具当作「已交付的保证」，但没有任何一条写明它的判定由哪条测试直接断言。

**DOC-10 是「验证器必须被验证」在文档侧的落点**：一个工具的判定只要写成 exit code 或手写登记表，文档就必须写明它的判定被哪条测试直接断言，而不是把无人执行的约定当成保证。

- **exit code 是断言**：必须写明「未解释幽灵 → exit 1、全部可解释 → exit 0」两条路径都被测试驱动，禁止只写「发现幽灵返回 1」。
- **登记表不可静默腐烂**：手写登记（如不可解析值登记）必须写明它的接收凭证由测试持续校验，条目一旦开始可解析即为陈旧，必须 FAIL。
- **单测不得依赖环境**：必须写明单测只扫合成语料、不触碰本机兄弟仓。
- **覆盖 ≠ 正确**：0 覆盖、exit code 无人断言的脚本，其判决只是一条未验证的声明。

**反例（loop cycle-23 A）**：cycle-22 交付的 `scripts/audit_cross_repo_ledger.py` 是分类器唯一调用方，此前 0 覆盖、exit code 从未被跑过；补 3 例后 27→30、全量 1615→1618 passed。第 8 例同族缺陷：**交付的验证器本身未被验证**。
