# architect-review 判断力指南（Guide）

> 单 atom 调用硬规则：交付必须含四件套——结论 / 证据（行级）/ 风险分级 / 下一步。
> 风险分级按 `reference/risk-grading-scheme.md` 量化口径判定。

# 架构审查与代码质量

## 审查方法

### 1. 双轴审查（code-review）

- **A轴 — 规范审查**: 代码是否符合项目规范（命名、结构、风格）
- **B轴 — 规格审查**: 代码是否实现了规格要求（spec/需求是否满足）
- **两轴独立**: 规范通过≠规格通过，反之亦然

### 2. Fowler 代码坏味道清单

| 坏味道 | 含义 | 信号 |
|--------|------|------|
| 神秘命名 | 变量/函数名不表达意图 | `x`, `tmp`, `data`, `process` |
| 重复代码 | 相同逻辑出现在多处 | 3次复制粘贴 → 提取 |
| 长函数 | 函数超过50行 | 拆分 + 提取意图命名 |
| 长参数列表 | 参数超过5个 | 用数据对象封装 |
| 全局数据 | 模块级可变状态 | `_SETTINGS = {}` → 注入 |
| 发散式变化 | 一个类因不同原因被修改 | 拆分为多个单一职责类 |
| 霰弹式修改 | 一个变化需要改多个类 | 合并相关逻辑 |
| 依恋情结 | 函数过度使用其他类的数据 | 移到数据所在的类 |
| 数据泥团 | 总是同时出现的数据项 | 提取为独立对象 |

### 3. Agent 架构审计维度（12层）

对 Agent/编排系统逐层检查：
1. System Prompt / 配置 — 是否正确加载？
2. Session 历史 — 有无上下文泄漏？
3. Memory — 模式库是否有污染？
4. 蒸馏/学习 — learn 步骤是否分类正确？
5. Tool 选择 — 分发逻辑是否覆盖所有类型？
6. Tool 执行 — 重试策略是否合理？
7. Tool 解读 — 结果解析是否正确？
8. 答案塑形 — 输出格式是否统一？
9. 渲染 — 展示层是否独立？
10. 隐藏修复循环 — 是否有自动修复陷入死循环？
11. 持久化 — 数据是否一致？
12. Scope — 隔离是否有效？

### 4. 质量门禁（Quality Gates）

| 级别 | 条件 | 阈值 |
|------|------|------|
| Green | 自动通过 | 无新增测试失败，无新增坏味道，测试覆盖率≥80% |
| Yellow | 警告（需关注） | 新增代码>200行无测试，重复代码块>5处，测试覆盖率 60%-80% |
| Red | 阻塞（不得合并） | 测试失败，关键路径改动无验证，测试覆盖率<60%，新增安全漏洞，数据迁移无回滚方案 |

## 证据化输出

每个发现都要能被另一位工程师复核，禁止只写“感觉有风险”。推荐格式：

```markdown
### [high] 事务跨越多个连接导致部分提交
- 位置: path/to/store.py:120-148
- 证据: `append_failure()` 与 `update_round()` 使用不同连接，异常时无法原子回滚
- 影响: 状态表和事件表可能不一致，恢复流程会重复执行
- 修复: 共享连接并用 `BEGIN IMMEDIATE` 包裹写入；增加回滚测试
- 验证: `npm test` / `pytest -q`（按项目实际命令替换）
- 置信度: 0.92
```

审查结论必须区分 `VERIFIED`（已运行命令或可定位证据）、`INFERRED`（由代码推断）和 `UNVERIFIED`（需要环境/业务信息）。发现按严重等级排序，并说明是否阻塞合并。

## 检查清单

```text
[ ] 是否读过项目规范、Spec 和迁移说明？ → 未读: 先收集上下文，避免把风格偏好当缺陷
[ ] 是否同时做了规范轴和规格轴审查？ → 只做一轴: 补另一轴并分别给结论
[ ] 每个发现是否有文件/行号、影响、修复和验证命令？ → 缺任一项: 标记为未完成发现
[ ] 是否检查安全、数据一致性、可观测性和回滚？ → 未检查: 追加对应维度或声明不适用
[ ] 是否运行了关键路径测试并记录结果？ → 未运行: 不能标记为 VERIFIED
[ ] 是否存在新增代码无测试、迁移无 rollback 或硬编码密钥？ → 存在: 至少 Yellow，关键路径直接 Red
[ ] 是否用半定量基线判结构健康（god-file >800 行/单文件 >30KB 离群）？ → 无基线: 按字节/行 Top-N 取离群文件；>阈值标 high；跨项目横评沉淀阈值
[ ] 被审项目是否有自评/已知问题清单？ → 无自评: 先催建自评清单再评，避免漏其已知盲点（C 类失效：起点低、无自评）
[ ] 若已有自评，是否配"还债门禁"（问题转任务+追踪关闭）？ → 评而不修: 标 high，要求自评项落入任务系统并设关闭判据（B 类失效：评而不修）
```

## 审查流程

1. 读 CLAUDE.md 了解项目规范
2. 扫描 git diff 或指定文件
3. 按双轴 + 坏味道清单检查
4. 按12层审计（如适用）
5. 输出带严重等级的发现列表

## 常见问题修复指南

### 全局可变状态 → 依赖注入
1. 找到模块级可变变量（如 `_SETTINGS = {}`）
2. 创建配置类封装，构造函数接收参数
3. 在入口处（如 Orchestrator.__init__）创建实例并传递
4. 删除全局变量，搜索所有引用替换为实例引用
5. 参见 [[architect-design]] 端口-适配器模式

### 长函数 (>50行) → 拆分
1. 识别函数的逻辑段落（用空行或注释分隔）
2. 每个段落提取为独立方法，用意图命名
3. 原函数变为协调方法，只保留调用顺序
4. 参见 [[architect-design]] 深模块设计

### 测试覆盖率 <60% → 补测试
1. 按模块排序覆盖率（从最低的补起）
2. 先补公共接口的 happy-path 测试
3. 再补边界条件（空输入、超时、异常路径）
4. 参见 [[architect-test]] TDD 铁律

### 数据一致性风险 → 加事务
1. 找到跨表/跨语句的写入操作
2. 包裹在 `BEGIN IMMEDIATE ... COMMIT` 中
3. 确保使用同一连接
4. 参见 [[architect-data]] 事务保护

### 结构健康半定量基线（god-file 尺）

- 单文件 >800 行 或 >30KB → 标 high（god-file），按职责拆分。
- 单类 >1500 行 / 函数 >50 行 → 坏味道（见上 坏味道表）。
- 定性结论需附数值证据；仅"感觉太大"而无数值的发现降级为 medium 以下。
- 跨项目横评沉淀的体积基线反哺 [[architect-design]]。
> **修复验证标准（必填）**：本节任一修复完成后，须给出**可运行验证命令 + 通过条件**或可观测判据；仅"我改了/已调整"不算完成（对照 Router 交付协议第 3 步）。
