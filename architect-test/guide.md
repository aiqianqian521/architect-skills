# 测试与质量保证

## TDD 铁律

### 红-绿循环
```
1. RED:    写一个失败的测试（只测公共接口）
2. GREEN:  写最少的代码让测试通过
3. REFACTOR: 重构代码，保持测试绿色
```

### 好测试的标准
- 只通过公共接口验证行为
- 一个测试只验证一个行为
- 测试名称描述场景（不是实现）
- AAA 结构：Arrange → Act → Assert

### 三类反模式
```
[ ] 实现耦合测试 — 测试绑定了内部实现细节（mock了不该mock的）
[ ] 同义反复测试 — getX() 的测试验证 x==x，无意义
[ ] 水平切片测试 — 按层测试而非按功能垂直切片
```

### 在哪写测试
- **接缝处**: 系统的自然边界（端口-适配器边界）
- 端口测试：用 fake 实现
- 适配器测试：用真实基础设施（集成测试）

## pytest 模式

```python
# 参数化
@pytest.mark.parametrize("input,expected", [
    (TaskInput("backtest", {}), "completed"),
    (TaskInput("unknown", {}), "error"),
])
def test_runner(input, expected):
    assert runner.run(input).status == expected

# Fixture 作用域
@pytest.fixture(scope="module")  # 模块级复用
def store():
    s = PatternStore(":memory:")
    yield s
    s.close()

# 使用 conftest.py 共享 fixture
```

## 调试方法论（diagnosing-bugs）

### 6 阶段诊断循环
1. **构建反馈循环**: 写一个能复现bug的测试（必须红）
2. **复现 + 最小化**: 缩减到最小可复现用例
3. **提出假设**: 3-5个可证伪的假说，按可能性排序
4. **逐一验证**: 每次只改一个变量
5. **先写回归测试**: 修复前写好测试，确保修复有效
6. **清理**: 移除调试代码

### 反馈循环构建方法（6 种）

| 方法 | 适用场景 | 操作 |
|------|---------|------|
| **失败测试** | bug 可以复现 | `@pytest.mark.xfail` 装饰器写一个红的测试 → 修复代码 → 测试变绿 |
| **curl/CLI 一行复现** | API/CLI 相关 bug | 复制触发 bug 的精确命令到终端，一行回车就能看到错误 |
| **重放 trace** | 有日志/事件流 | 从 JSONL 提取触发 bug 的那条 event → 用同样输入重新执行 → 对比结果 |
| **临时 harness 脚本** | 需要反复调试的模块 | 写 `_debug_xxx.py` 单文件脚本，只加载目标模块的最小依赖，循环执行直到复现 |
| **Bisection 二分定位** | 大规模改动后引入的 bug | `git bisect start` → `git bisect bad HEAD` → `git bisect good <last-known-good>` → 逐个 commit 测试 |
| **差异对比** | 正常 vs 异常 | 并排对比一次成功的执行 trace 和一次失败的 trace，逐行找出第一个不同的地方 |

## 契约、集成与黄金数据集

测试层级按系统边界组织，而不是按内部类层级堆叠：

| 层级 | 目标 | 替身策略 |
|------|------|---------|
| 领域/用例单测 | 验证业务规则和编排结果 | fake outbound port；不 mock 被测内部实现 |
| 契约测试 | 验证端口的输入、输出、错误和幂等契约 | 同一套契约跑在每个适配器上 |
| 集成测试 | 验证真实 DB/API/队列的序列化、迁移、超时和重试 | 使用隔离资源，测试后清理 |
| E2E/回归 | 验证关键用户旅程和发布不回归 | 最少但稳定，失败输出完整 trace |

对 Agent、推荐系统和复杂数据转换，维护一个版本化 golden dataset：每条样本包含输入、期望状态/决策、允许的误差、来源和脱敏说明。每次变更运行固定子集和全量回归，报告通过率、边界样本和已接受差异；不能只报告平均分。

测试数据需要可重复生成，固定 seed 和时间；敏感生产数据必须脱敏或合成。任何新豁免都要写明原因、owner、到期日和复审测试。

## 检查清单

```

[ ] 测试是否通过公共接口？（没有mock内部实现） → 有mock内部: 改为只mock端口（ABC），适配器用 fake
[ ] 测试命名是否描述场景？ → 命名模糊: 改为 test_<what>_<condition>_<expected> 格式
[ ] 是否覆盖了边界条件？（空输入、最大值、超时） → 补: @pytest.mark.parametrize 加边界用例
```

## 常见问题修复指南

### Flaky 测试 → 确定性化
1. 找到使用 random/当前时间的测试
2. 用 `random.seed(42)` 或 `freezegun.freeze_time()` 固定
3. Mock 外部依赖返回固定数据
4. 连续跑 10 次确认不再随机失败

### 测试不足 → 补覆盖
1. 按模块运行 `pytest --cov` 看覆盖率报告
2. 优先补覆盖率最低的模块
3. 先公共接口 happy-path，再边界条件，最后异常路径
4. 参见 [[architect-review]] 质量门禁阈值

> **修复验证标准（必填）**：本节任一修复完成后，须给出**可运行验证命令 + 通过条件**或可观测判据；仅"我改了/已调整"不算完成（对照 Router 交付协议第 3 步）。

## cycle-17 实测增补：门禁自证（2026-10-23）

> 来源：cycle-17 A —— 对"守护者本身的守护"做审计（真值 file:行段：`contract.json` TES-12 / TES-13）。
> 口径：**一个守护脚本如果只被"源码 grep"验证，它就没有被验证；一个登记数字如果从不与实测对照，它就不是约束。**

**TES-12 · 收集扫描必须覆盖 pytest 的全部可收集命名与深度**：门禁"防伪测试"的扫描器自己也会漏——
`glob('test_*.py')` 非递归且只认 `test_` 前缀，而 pytest 默认 `python_files = test_*.py *_test.py` 且**递归**收集。
做法：扫描器用 `rglob` 匹配两种命名；再加一条**扫描器自证用例**（在 tmp 目录里放 `test_a.py` / `b_test.py` /
`sub/test_c.py` / `helper.py`，断言只看到前三个）。真值：loop cycle-17 —— cycle-16 的 tripwire 可被
`tests/<sub>/…` 或 `foo_test.py` 整体绕过，且当时无人能发现，因为扫描器本身没有测试。

**TES-13 · 登记基线数字必须与实测运行对照（单向棘轮）**："基线"必须同时被钉在**两个方向**：
① 文档 == 登记（已有）；② 实测 >= 登记（本次补）。缺 ② 时的失效模式是**静默删测试**：删掉一批测试、
手改登记值与文档，门禁全绿。做法：门禁跑完测试后解析摘要（`N passed` / `Total coverage: X%`）与登记值做
**单向棘轮**比对（实测 < 登记 = 失败；多出 = 允许，因为那是新增测试），摘要解析失败也判失败（fail-closed）；
覆盖度比对留一个小的浮点/取整容差，避免第二位小数抖动误报。真值：loop cycle-17 —— `run_gate.py` 原先
只检查 pytest 退出码与 `fail_under`，`docs/baseline.json` 的 `passed`/`coverage` 从未与实测对照过。

## cycle-18 实测增补：提交链自证（2026-10-23）

> 来源：cycle-18 A —— 对"唤醒指针 / 文档里的提交链"做审计（真值 file:行段：`contract.json` TES-14）。

**TES-14 · 文档/指针里的提交链与哈希引用必须被机器校验**："守护者无人守护"的第三处（cycle-16 修被门禁漏掉的测试、
cycle-17 修门禁自身、cycle-18 修唤醒指针的提交链）。凡是"记录型"文档 —— 提交链、`head <hash>`、基线数字 ——
都必须有脚本解析**活文档**并与真值（git 历史 / 单一事实源）对照：

- ① 每条 `cycle-N` 哈希须在 git 中真实存在；② 提交主题里的 cycle 号不得与标注矛盾；③ 同一哈希不得标注两个 cycle；
  ④ 链的标题跨度须等于最新条目；⑤ 指针 `head` 须等于单一事实源（如 `docs/baseline.json.head`）。
- fail-closed：链段落 / 指针定位不到 = 失败（禁止"解析不到就跳过"）；跨仓条目（architect-skills B）在兄弟仓存在时
  一并校验，缺失时登记为机器本地缺口，**不降级**为静默通过。
- 守卫自身必须有负例：把真实文本改回缺陷态必须立即报错（loop cycle-18：错标注 / 重复哈希 / 标题跨度 / 锚点丢失 /
  head 漂移 共 4 条负例）。
- 性能也是门禁质量：git 查询要批量化（每仓一次 `git log --all` + 记忆化），逐条目 spawn 会让守卫本身变成负担
  （loop cycle-18 首版 ~45s → 10s）。

反例（loop cycle-18 实证）：`docs/flow/GRAND-LOOP.md` 的提交链把 cycle-16 A 记成 `710a3af`（实为 cycle-17 A），
真正的 `a09421a` 全文 **0 次出现** —— 重复的 `710a3af` 把缺失掩盖成"看起来完整"，且没有任何门禁报警，
照链取证的 agent 全部拿到错哈希。

## cycle-19 实测增补：缺陷引用不得伪装成声明（2026-10-23）

> 来源：cycle-19 A —— 对"缺陷 / 负例的写法"做二次审计（真值 file:行段：`contract.json` TES-15）。

**TES-15 · 缺陷/负例引用必须与机器可读的声明形态可区分**：cycle-18 修好了"提交链与真值不一致"，但
**缺陷描述本身**又在设计文档、status §13.43、工作记录里原样照抄了错哈希的声明形态（`` `710a3af`(cycle-16 A） ``），
全仓扫描立刻在 3 处复现同一个假声明 —— **缺陷记录把缺陷又造了一遍**。规则：

- 机器要解析的声明用**固定形态**（如 `` `hash`(cycle-N …) ``）；提到错值时必须让该形态**无法匹配**：
  写成 `` `hash`(❌错记 cycle-N …) ``，或在哈希与 cycle 之间插入说明文字，并在引用块顶部加图例。
- 栅栏内的"修复前原文照抄"也必须加标记，且全仓扫描必须同时覆盖**设计文档 / status / 交接记录**，
  不能只扫"被修复的那个文件"。
- 扫描要有覆盖度自证（命中数 >= 阈值）与负例自证（改坏一处必须报错），否则"扫不到"与"没有问题"无法区分。
- **扫描覆盖待提交文件**：只扫 tracked 会让“正在写的新文档”逃过扫描，而它恰恰在提交后才被守卫发现（loop cycle-19 A2：`git ls-files` → `--cached --others --exclude-standard` + 本机工作记录）。提交前必须能看见即将提交的内容。
- 反例（loop cycle-19 实证）：`test_no_tracked_document_claims_a_hash_for_the_wrong_cycle` 首跑即报 3 条 ——
  两条在 cycle-18 设计文档、一条在 status §13.43；工作记录（未纳入版本控制的 `work_ooda/`）也有 1 条，一并修掉。

写作启示：**修完"记录错了"之后，还要修"记录里写着那个错"** —— 否则下一个取证脚本会把否定句读成肯定句。

## TES-16 · 正文散文里的哈希引用必须被机器校验（存在性 + 箭头链拓扑）

> 来源：cycle-20 A —— 用户直问「任何照链取证的 agent（回溯代码、写交接、做归因）都会拿到错哈希，而错哈希会被当成事实一路传递」。

**TES-16 · 账本正文里的哈希引用必须可解析**：cycle-18/19 守住了 `` `hash`(cycle-N) `` 声明形态与唤醒指针区块，但**正文散文里的裸哈希与 `A→B→C` 箭头链从未被任何守卫看过**。loop-dev-next 三仓交叉取证（loop-dev-next / legacy loop-dev / architect-skills）命中 3 个幽灵哈希：

- `docs/flow/GRAND-LOOP.md` L53 legacy 补充链把 ❌错记 `11588a1` 当作 `1fb4846→…→edf2a55` 的真实中间提交 —— 三个仓都解析不出；真值 `11542a1`（`edf2a55` 的真实父提交）。
- `docs/design/2026-10-22-cycle14-C-state-history-export.md` L4 把它**自己的** step A 提交写成 ❌错记 `a67594c`；真值 `a67594e`。
- `docs/flow/2026-09-05-grand-loop-status.md` §13.9 把建 `loop-engine/backpressure.py` 的提交写成 ❌错记 `8cf9d4c`；真值 `eb9f4b6`。

规则要点：

- 每个反引号哈希、箭头链里的每个哈希都要在**已知仓**里解析得出；解析不出 = 幽灵，fail-closed。
- 箭头链里**同仓相邻**哈希必须**祖先相关**（用一次 `rev-list --all --topo-order --parents` 建祖先表，别逐对 spawn）；真实但乱序也要拦。
- 只扫反引号哈希与箭头链：`20261023` 这类日期同样匹配 `[0-9a-f]{7,40}`，全裸扫误报不可接受 → 约定「提交哈希一律反引号」。
- 跨仓箭头只做存在性（跨仓祖先关系无定义）。
- 引用缺陷值必须**同行标记**（❌错记 / phantom / NOT-A-COMMIT），否则视为声明。

**二次自证（同 cycle-19 A2 家族）**：守卫自证探针里放一条**带反引号**的乱序箭头链 → 守卫**没报**。根因：`ARROW_RUN_RE` 只认裸哈希，带反引号的箭头链整段漏检。修：匹配前把反引号展平为空格（tokenizer 与拓扑检查**两处**）。教训：**守卫的自证必须覆盖「守卫自己宣称能抓的每一种形态」**。

写作启示：**「没人校验的记录」=「还没被发现的错」**；守卫的说明与守卫的能力一旦脱节，脱节本身就是一次「记录 vs 真值」。

## TES-17 — 正文/指针里「裸写」的提交哈希也必须被机器校验（同行 git 上下文门控 + 外部源仓 pin 登记）

> 触发：loop cycle-21 A。用户在 cycle-20 之后追问「任何照链取证的 agent 都会拿到错哈希，而错哈希会被当成事实一路传递，这个修复了嘛？」——复查发现 cycle-20 只扫**反引号哈希与箭头链**，**裸写（无反引号）的哈希从未被任何守卫看过**。

**TES-17 — 裸写的哈希引用必须可解析**：GRAND-LOOP 的**唤醒指针路径行**（`HEAD 1fb4846 … 362e479/af5cd11`）与 registry 的**提交列**（`766209c/24be2bb/56b1b6e`）都在**不带反引号**的散文里写提交哈希；全仓扫描实测 **79 个唯一裸 token（179 处）** 从未被任何守卫看过。

- 裸哈希**仅当同一行已含至少一个可解析提交引用**时才视为提交引用（该「共现门控」排除 defaced/effaced 这类全 hex 英文词——裸扫必然误报；实测当前语料 0 误报）。
- 该裸哈希须在已知仓中**真实存在**，解析不出 = 幽灵哈希，**fail-closed**。
- **外部源仓 pin**（`SOURCE.md` 的 `TencentDB-Agent-Memory@2ee2239`）须**登记对应 checkout** 后解析——否则会把真 pin 误判为幽灵（这正是裸扫的第一个假阳性来源）。
- 带 `md5=`/`sha256:` 等**摘要标签**的行跳过；**纯数字 token 仍排除**（`20261014` 这类日期会同现于 git 上下文行，实测会误报）。
- 引用缺陷值必须同行标记。

**自证**：向仓库根放一个含裸 abc123d（同行含真哈希）的未跟踪 `.md` → 守卫立刻 FAIL；删除后恢复 0 违规。方法论：**每加一层守卫，先证明它抓得住「已知坏样本」，再证明它在当前语料上不误报**。

## TES-18 — 跨仓/多语料账本扫描：先把「合法不可解析值」分类出去，默认仍是 fail-closed 幽灵

> 触发：loop cycle-22 A。cycle-18~21 造出的账本守卫一直在**一个仓**里自我校验；cycle-22 第一次把同一套规则指向兄弟语料（legacy `loop-dev` 2300 篇 shipped `.md`、architect-skills 86 篇）。

**TES-18 — 多语料扫描必须先分类，再判 fail-closed**：同一套「哈希必须可解析」规则，在本仓是门禁，指向外部语料就是**假阳性机器**（实测 32 处 finding、0 处幽灵）。必须：

- 不可解析值**逐类**给出可复现的排除规则：① 数据指纹（行内 md5/sha/checksum/digest/input_hash/指纹 标签，或 16/32/64 位 hex）；② 运行时对象 id（容器 / pod / sandbox / crictl 语境，**文档级**判定）；③ 被 amend 掉的中转提交与外部仓基线（显式登记表，逐条带出处）；④ 守卫自身示例（TES-15 家族的延续）。
- 分类器**默认仍是幽灵**（fail-closed）：解释不了的 token 依旧报错。
- 分类器**只用于取证报告**，禁止接入门禁 —— 否则「16/32 位一律算摘要」会顺手豁免伪造的提交声明。
- 语料边界必须写明：只扫 shipped `.md`；机器可读契约 JSON 里的规则文案不算账本。

**自证（双反方向）**：① 语料里放一条**无标签、无运行时上下文、未登记**的 7 位哈希 → 必须报幽灵；② 同一枚 token 在有 md5 标签的行判指纹、在无标签行判幽灵。loop 侧 `scripts/audit_cross_repo_ledger.py` 复现整轮跨仓扫描，unexplained 0 才 exit 0。

## TES-19 — 交付的验证器/取证工具本身必须被验证：exit code 是断言，登记表不可静默腐烂

> 起因：loop cycle-23 A。cycle-22 交付的跨仓取证脚本是分类器唯一调用方，0 覆盖、exit code 无人断言——「交付了验证器」≠「验证器被验证」。

**TES-19 是「验证器必须被验证」的第 8 个面**：把判定写成 exit code 或一张手写登记表，就必须有测试直接驱动它，而不是只在文档里写约定。

- **exit code 是断言**：合成语料里放一条未解释幽灵 → 必须 exit 1；全部可解释 → 必须 exit 0。两条路径都要被断言。
- **登记表不可静默腐烂**：手写登记（如 REGISTERED_UNRESOLVABLE）必须由测试持续校验——每条此刻仍解析不出任何已知仓；某条开始可解析 = 陈旧凭证 = FAIL。
- **单测不得触碰本机兄弟仓**：清空默认扫描目标、只扫合成仓，否则测试退化成环境依赖。
- **覆盖 ≠ 正确**：0 覆盖的工具，其判决只是一条未验证的声明。

**反例（loop cycle-23 A）**：`scripts/audit_cross_repo_ledger.py`（cycle-22）是 `classify_document` 的唯一调用方，此前 0 覆盖、exit code 从未被跑过；补 3 例后 27→30、全量 1615→1618 passed。第 8 例同族缺陷：**交付的验证器本身未被验证**。

## TES-20 — 校验器的「作用域」（手写校验清单）本身必须被校验：入口文档不得被排除

> 起因：loop cycle-24 A。cycle-17 的 `docs_baseline.py` 用一张手写清单防止当前态文档漂移，但清单里没有「第一个被 agent 读的」wake pointer。

**TES-20 是「验证器家族」的第 9 个面**：cycle-23 说「判决必须被测试」，本轮再往外一层——**「被判定的对象集合」也必须被测试**。

- **入口文档不得缺席**：wake pointer 引用的基线数字若无校验，就是「最该被信任的文件恰恰没人查」；
- **清单本身要被断言**：有测试固定「入口文档在清单内」，否则清单可静默缩水；
- **自证**：把入口文档的数字改坏，校验器必须 FAIL（否则等于没接上）；
- **边界要写清**：历史 / 快照文档不纳入是刻意的；入口文档漏掉不是刻意的。

**反例（loop cycle-24 A）**：`docs_baseline.CHECK_FILES` 覆盖 9 份当前态文档却漏掉 `docs/flow/GRAND-LOOP.md`；改成 `9999 passed / coverage 55.55%` 后 docs_baseline 仍 OK、wake-pointer 守卫仍 30 passed。补 3 例后 1618→1621。第 9 例同族缺陷：**校验器的作用域无人校验**。

## TES-21 — 『指向下一步』的导航标号必须被机器校验：指针等于注册表最新号，注册表连续无重复

> 起因：loop cycle-25 A。GRAND-LOOP.md 的『下一目标（自动，按 §13.N 排序）』是一个手写指针，每轮 C/D 手动 +1；状态注册表的最新小节由人工追加。此前没有任何校验。

**TES-21 是「指针家族」的第 10 个面**：cycle-18/19/21 校验的是哈希指针（提交链 / 裸哈希 / 外部 pin），本轮校验的是**标号指针**（章节号 / 序号）。

- **指针 = 注册表最新**：指针标号必须等于注册表里最新的 `### 13.N` 小节；过期指针会把下一个执行者引到旧的『下一目标』清单；
- **注册表 append-only**：编号必须连续、无重复；缺号 / 重号即违规；
- **fail-closed**：指针缺失、注册表为空，都算失败；
- **自证**：把指针改成过期编号必须 FAIL；制造重号 / 缺号必须 FAIL。

**反例（loop cycle-25 A）**：把 `docs/flow/GRAND-LOOP.md` 的指针从 §13.50 改成过期 §13.49 → `tests/test_wake_pointer_chain.py` 仍 30 passed、`docs_baseline` 仍 OK。补 4 例后 30→34、全量 1621→1625。第 10 例同族缺陷：**导航指针无人校验**。
