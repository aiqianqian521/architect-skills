# 评估工单迭代跟踪模板（Iteration Tracker Template）

> 关联：`docs/蜂群改造实施计划.md` 主线 3「评估→矫正闭环」（B7）
> 用途：跟踪"发现 → 矫正 → 验证 → 关闭"闭环。当前先用手工 markdown 表沉淀两轮，出现"撑不住"证据（见 §六）再脚本化（B11）。
> 状态：工作草案 v0.1

---

## 一、表结构

```markdown
| 发现ID | 维度 | 代理 | 风险 | 矫正项(改什么/怎么改/验证/回滚) | 状态 | 验证代理 | 关闭证据 | 方案版本 |
|--------|------|------|------|--------------------------------|------|----------|----------|----------|
```

字段语义：
- **发现ID**：稳定唯一，跨轮不变（如 `M5`、`Q1`、`C1`）。
- **矫正项**：必须含四件套——改什么 / 怎么改 / 验证（可运行命令）/ 回滚。
- **状态**：`open → in-fix → verifying → closed`（见 §二状态机）。
- **关闭证据**：必须是一条可运行验证命令 + 通过结果；**无证据不得 closed**。
- **方案版本**：该发现对应的方案/代码版本（如 commit、date），用于跨轮比对是否已变动。

---

## 二、状态机

```
open ──指派──▶ in-fix ──提交验证──▶ verifying ──证据通过──▶ closed
                  │                      │
                  └──退回──▶ open         └──证据不过──▶ in-fix
```

| 迁移 | 必须携带的证据 |
|------|---------------|
| `open → in-fix` | 负责人指派记录 |
| `in-fix → verifying` | 矫正项已实现的 diff/描述 |
| `verifying → closed` | **可运行验证命令 + 通过结果**（缺一不可设 closed） |
| `verifying → in-fix` | 复验失败的命令输出 |
| `in-fix → open` | 方向重估、矫正项被否的决定记录 |

硬约束：
1. **关闭证据缺失不得 closed** —— 只有"改好了"没有"验证命令通过"一律不许标 closed。
2. `closed` 项在下一轮蜂群复评中**默认跳过**，除非方案版本变更后被重新拉起。

| 发现ID | 维度 | 代理 | 风险 | 矫正项 | 状态 | 验证代理 | 关闭证据 | 方案版本 |

## 四、下一轮复评只看什么

1. 上一轮 **未关闭**项（open/in-fix/verifying）——先核这些是否本次已变。
2. 本次**新增**项（新发现）。
3. **忽略**已关闭且方案版本未动的旧项。

---

## 五、怎么用（一轮闭环的步骤）

1. 蜂群跑一轮 → 各维产出发现清单。
2. 对照已有工单表：命中既有 ID 则更新其状态/方案版本；否则新增行。
3. 每个 critical/high 填满矫正四件套；缺验证命令的项标 `unknown`，不进 closed。
4. 下一轮复评开始时，先把 open 且版本未动项列为首要核查对象。

---

## 六、什么信号出现才脚本化（B11 触发判定）

出现以下任一证据，即认定"手工表撑不住"，才投入脚本化：
- 单轮发现数 > 30，手工维护持续出错（增删行对不上）；
- 跨两轮时发现同一 ID 状态漂移/重复（人工更新漏同步）；
- 需要按"维度/代理/风险"多维筛选、排序时，手工表已无法满足；
- 跨项目（≥2 个）复用同一张表，出现合并冲突。

未出现前，坚持手工 markdown 表，不为确认性问题预建系统。
