## 一、P1（critical）PROPOSAL 门禁误用：评估现有项目被标为"已阻塞"

### 现象（实测可复现）
- 三份实测报告头部均含 `## 门禁判定：❌ PROPOSAL_INCOMPLETE`，横幅"方案不完整，缺失字段：target, gap, migration, compat, acceptance, owner"。
- `tests/fixtures/eval-*.json` 三个真实评测输入**均无 `proposal` 字段**（因为是"评估现有项目"而非"评审改造方案"）。
- 我用 `node scripts/render-report.cjs tests/fixtures/eval-cspm-agent.json` 复现：exit=0，但输出顶部仍是 `PROPOSAL_INCOMPLETE` 门禁横幅。

### 根因
`scripts/render-report.cjs` 的 `computeVerdict`：
```js
if (!proposalCheck.complete) {
  return { pass: false, label: "PROPOSAL_INCOMPLETE", ... };
}
```
`validateProposal(undefined)` 对缺失 proposal 一律返回 `{complete:false, missing:[6字段], level:"critical"}`。系统没有区分两类任务：
- **assessment mode**（评估现有项目，proposal 可空、不应阻塞）
- **review mode**（评审改造方案，proposal 必填、缺失即门禁）

### 影响
用户看到"已阻塞、方案不完整"却拿到的是一份其实已跑出 findings 的报告，观感和语义都误导；`PROPOSAL_INCOMPLETE` 出自场景 B 的"方案评审表"，被错误地应用到了纯评估场景。

### 建议
- 给 renderer 增加显式 `mode`（`assessment`/`review`）参数：
  - `assessment` 下 proposal 缺省**不**判不通过，正常全维渲染；
  - `review` 下才启用 `PROPOSAL_INCOMPLETE` 门禁。
- 相关字段来自 `docs/proposal-review-schema.md`，需在该文档补"模式区分"章节。

## 二、P2（major）reflection 四段可为空且无任何校验

### 现象
- 三份实测报告的「结论叙述 / 关键发现 / 加固建议 / 下一步」四段**全部为空**。
- 渲染代码：
```js
const n = input.narratives || {};
out += "## 结论叙述\n\n" + (n.summary || "") + "\n\n";
out += "## 关键发现\n\n" + (n.keyFindings || "") + "\n\n";
...
```
即使 narratives 完全缺失也只输出空段，不告警、不 throw。

### 根因
- 渲染层把 narrative 当"可选"，而测试方案/金样对口径要求 narrative 必须有实质内容（金样 INDEX 要求"结论/证据/风险分级/下一步"四件套）。

### 建议
- 在校验层把 `narratives.summary` 设为必填（或至少是高度建议），缺失时 strict 模式 throw、lenient 模式显式标 `⚠️ NARRATIVE_MISSING`。
- 可在 `aggregateAgents` 后自动生成一句话 summary 兜底，减少空段。

## 三、P3（major）N/A 维度被标成 missing

### 现象
- loop-dev 是本地 CLI 回测工具，其 `net/cost/compliance/frontend` 等维度本应判 N/A（带复检条件），但实测报告「② 覆盖矩阵」把它们标为 `missing`（0 证据）。
- 渲染逻辑：
```js
const status = cov ? cov.status : (findings.length ? "covered" : "missing");
```
没有任何 `not-applicable`/`N/A` 的判定。

### 根因
- 既有 `reference/cross-project-input-format.md` 与 `reference/risk-grading-scheme.md` 都定义了 `N/A（not-applicable / N-A）` 状态及其复检触发条件，但新版 renderer 未实现 N/A 计算。

### 建议
- 在聚合/渲染层补 N-A 判定：无 agent 产出、且经规则判定维度不适用的，输出 `N/A`（附复检触发条件），而非 `missing`。
- 与既有契约对齐状态枚举（见 P7）。

## 四、P4（major）① 项目架构地图恒为占位符

### 现象
- 三份实测报告「① 项目架构地图」均为"（由评估者据 Intake 建图填写；renderer 强制本节存在。）"占位。
- `tests/fixtures/eval-*.json` 无 `archMap` 字段；渲染逻辑 `const archMap = input.archMap || [];` 直接空数组 → 占位。

### 根因
- 各 agent 的 `meta.files_read` / `meta.intake_evidence_count` 其实已含建图证据（如 cspm 的 app.py、task_service.py、Dockerfile），但 renderer 没有从 agent meta 自动推导 archMap，导致有证据却不出图。

### 建议
- 让 renderer 从所有 agent 的 `meta.files_read` + `findings.file_line` 自动聚合一个最小架构地图（去重目录 → 职责 one-liner 可标注"待补"），避免恒占位。
- 或要求 orchestrator 分发前强制提供 archMap。

## 五、P5（major）契约分层只做了 1 个 atom，其余 15 个缺失

### 现象（实测确实）
- 16 个 atom 目录中，**只有 `architect-security/` 含 `contract.json / guide.md / SKILL.md`** 三件套；其余 15 个（design/test/data/...）仅 `SKILL.md`。
- 运行 `node scripts/validate-contracts.mjs` 扫描 16 个 atom：**15 个 ERROR**（"contract.json 缺失（必须拆分契约层）"），仅 security 通过。exit=1。

### 根因
- B4 主线原计划是"先 single security atom 试点验证，再铺开"，但**试点之后扩到全量这个动作没有完成**；而 `docs/自我能力评估.md` 声称"为 15 个 atom 各写一套契约 schema"能独立完成，与实际不符。

### 建议
- 明确当前是"试点阶段"而非"全量完成"：`validate-contracts.mjs` 的 15 个 ERROR 要么作为**待办清单**推进铺开，要么调整校验为"允许未拆分 atom 以 warn 通过（试点期）"，避免校验永远红。

## 六、P6（major）测试方案承诺的 L1 单测实际不存在

### 根因

### 现象
