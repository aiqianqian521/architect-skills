# architect-skills 蜂群模式改造提案

> 提案日期：2026-08-31
> 针对场景：agent 蜂群（swarm）结合 architect-skills 对项目进行分布式架构评估
> 当前状态：architect-skills 为单代理深度评估设计，蜂群模式下出现 orchestrator 失效、证据口径不一致、修复归属不清等问题

---

## 一、当前蜂群使用模式的判断

### 已验证的优势（loop-dev effectiveness-check 为证）

| 优势 | 证据 |
|------|------|
| 突破注意力瓶颈 | 单个 LLM 无法同时深评安全、数据、成本、合规。蜂群让每个代理只盯一维。 |
| 交叉验证 | Bacon 发现 M5 masked bug，单代理 GREEN 测试未 catch。 |
| 责任可追溯 | 每条发现带代理署名（Bacon M5、Archimedes Q1），方便复盘。 |

### 已暴露的隐患（loop-dev 报告为证）

| 隐患 | 证据 | 根因 |
|------|------|------|
| Orchestrator 失效 | Halley verdict "did not surface via wait_agent (`completed:null`)" | 设计审查代理结果丢失，无显式缺失标记机制 |
| 证据口径不一致 | Bacon 说 threshold-restore masked，Archimedes 说 backward-compat omitted | 两代理证据无标准合并协议 |
| 修复归属不清 | M5 Bacon 发现，修复后 Bacon 验证，但无自动闭环跟踪 | 缺乏评估迭代/工单系统 |

---

## 二、技术角度改造建议

### 改造 1：atom SKILL.md 拆为「契约 + 指南」两层

当前每个 atom 是混合体（原则 + 检查清单 + 修复指南混在一起）。蜂群模式下，agent 只读契约就够了。

**目标结构**：
```
architect-security/
├── contract.json          ← 机器可读：检查清单、触发条件、输出 schema
├── guide.md               ← 人/LLM 参考：原则、示例、修复范式
└── SKILL.md               ← 保留，但变薄，引用 contract + guide
```

**contract.json 示例**：
```json
{
  "dimension": "security",
  "checklist": [
    {"id": "SEC-01", "rule": "所有外部输入白名单校验", "trigger": "发现拼接 SQL 或裸 eval", "severity_if_fail": "critical"}
  ],
  "output_schema": {
    "required": ["conclusion", "evidence_file_line", "risk_level", "next_step", "confidence"]
  }
}
```

**收益**：蜂群里的 Bacon 只需要知道"我要查什么、输出格式是什么"，不需要读 148 行的安全原则。减少 token 消耗，降低代理自由发挥空间。

---

### 改造 2：新增 `swarm-orchestrator.md`（蜂群编排契约）

当前 architect-router 只处理"用户意图 → 单个 atom"。蜂群模式需要显式定义任务分发、证据合并、冲突仲裁。

**核心条款草案**：

```markdown
## 任务分发规则

| 维度 | 执行代理 | 输入依赖 | 输出约束 |
|------|----------|----------|----------|
| security | SecurityAgent | Intake 建图结果 | 必须含行级证据 |
| test | TestAgent | Intake 建图结果 + 代码变更范围 | 必须含验证命令 |
| design | DesignAgent | Intake 建图结果 + 全部维度结论 | 最后执行，做全局调和 |

## 冲突仲裁规则（优先级降序）

1. **安全维度一票否决**：security agent 定 critical → 无论其他维度怎么说不，整项目阻塞。
2. **证据优先于推断**：有行级证据的 agent > 只有推断的 agent。
3. **耦合度优先于单维最优**：design agent 和 test agent 冲突时，按"最小破坏现有代码"原则调和。
4. **人工决策兜底**：上述规则无法调和时，标记为 `NEED_HUMAN_DECISION`，不自动选边。

## 证据合并协议

1. 所有代理输出统一为 JSON，字段：`agent`, `dimension`, `findings[]`
2. 同一文件同一行被多个代理引用 → 合并为一条，保留所有代理视角
3. 同一文件不同代理结论矛盾 → 标记为 `CONFLICT`，触发仲裁规则
```

### 改造 3：升级 `render-report.cjs` 为「强约束聚合器」

当前 renderer 是 60 行占位符，空 section 只输出提示文字。蜂群模式下，它应该是所有 agent 输出的唯一聚合入口。

**输入**：各 agent 的 JSON 输出
**输出**：统一的 L2 报告（五段结构）

**核心逻辑升级**：
```javascript
function aggregate(agentOutputs) {
  // 1. 证据去重：两个 agent 引用同一行，合并为一条
  // 2. 冲突检测：标记矛盾建议（如 design 建议合并，test 建议拆分）
  // 3. 风险升级：任一 agent 定 critical，该维即为 critical
  // 4. 空 section 拒绝：必填字段缺失时 throw，不生成半成品报告
  // 5. 置信度过滤：confidence=unknown 的发现单独汇总到「待复核」章节
}
```

**关键变化**：从"LLM 自由写 narrative，renderer 格式化"变为"agent 填结构化数据，renderer 强制装配"。

---

### 改造 4：引入「评估置信度」和「未知项」显式标记

当前 risk-grading-scheme 只有等级，没有置信度。蜂群模式下，agent 可能拿不到证据或沉默失败。

**扩展 risk-grading-scheme**：

| 置信度 | 定义 | 处理方式 |
|--------|------|----------|
| `high` | 读到直接证据（如明文密钥、god-file 行数） | 直接入报告 |
| `medium` | 基于间接推断（如"该模块可能缺乏输入校验"） | 入报告，标记需复核 |
| `low` | 仅基于模式匹配，无代码级证据 | 入「待复核」章节 |
| `unknown` | 代理无法完成评估（如 Halley completed:null） | **必须显式标记**，不能跳过 |

**收益**：解决 Halley `completed:null` 这种沉默失败问题。当前用户以为设计审查通过了，实际是代理失联。

## 三、架构师角度改造建议

### 改造 5：把「10 步固定顺序」改为「DAG 依赖图」

当前全面分析是线性 10 步。蜂群模式下，某些维度天然并行。

**建议 DAG**：
```
Intake 建图
    │
    ├──→ security（安全审查）
    ├──→ data（数据审查）         ← 并行，互不依赖
    ├──→ test（测试审查）
    ├──→ net（网络审查）
    │
    ↓（依赖上述结果）
    ops（运维审查）               ← 需要知道部署形态
    observability（可观测性）      ← 需要知道运行态
    │
    ↓（依赖全局）
    cost（成本审查）              ← 需要知道所有资源
    compliance（合规审查）         ← 需要知道所有数据处理
    │
    ↓
    design（设计调和）            ← 最后执行，仲裁跨维度冲突
```

**收益**：蜂群 orchestrator 可以按 DAG 调度，缩短总评估时间。

---

### 改造 6：增加「维度间冲突检测」专用代理

当前 architect-skills 只关注单维度。但蜂群评估必然产生跨维度矛盾。

**典型冲突场景**：
- design 建议"合并 orchestrator 与 controller"（减少边界）
- test 建议"拆分 orchestrator 与 controller"（便于 mock）
- ops 建议"独立部署 controller"（灰度需求）

**解决方案**：增加 `architect-arbiter`（仲裁代理）或让 router 承担：
1. 收集所有维度的建议清单
2. 用关键词/结构匹配发现冲突对
3. 按业务优先级（SLO > 成本 > 可维护性）给出调和方案
4. 无法调和的标记 `NEED_HUMAN_DECISION`

---

### 改造 7：把「金样回归」从人工重评改为「实时锚定 agent」

当前金样回归：改了模板 → 人工重评项目 → 对照旧金样。

**方案**：增加常驻代理 **RegressionGuard**
- 不评项目，只审计其他 agent 的输出
- 自动对比历史金样：同样条件上次定 high 这次是 medium → 触发"口径漂移告警"
- 对比跨项目基线：god-file 阈值 800 行，本次评了 750 行未标 high → 触发"基线遗漏"

**收益**：给蜂群加质量门禁，防止 agent 随时间退化或口径漂移。

---

### 改造 8：引入「评估迭代」机制（评估工单系统）

从 loop-dev 可以看到，架构评估不是一次性的：

```
P1.2 评估 → 发现 M5/M1/M2/M4/Q1/Q2 → 修复 → 第二轮验证 → ADR-008 记录
```

但当前 architect-skills 没有跟踪机制。建议增加：

```markdown
## 评估迭代跟踪

| 发现ID | 代理 | 维度 | 风险 | 修复状态 | 验证代理 | 关闭证据 |
|--------|------|------|------|----------|----------|----------|
| M5 | Bacon | test | medium | closed | Bacon | test_close_event_records_probe_success_count |
| Q1 | Archimedes | data | medium | closed | Archimedes | test_restore_pre_slice2_snapshot |
```

**收益**：下一轮蜂群评估时，只需关注：
1. 上一轮未关闭项
2. 代码变更引入的新增项
3. 忽略已关闭且代码未动的旧项

## 五、一句话总结

> 蜂群 + architect-skills 已经是业界最前沿的 AI 架构评审实践。当前最大瓶颈不是 agent 不够聪明，而是 architect-skills 没有为分布式评估设计契约层和编排层。**改造方向：让 skill 退化为"评估标准契约"，让蜂群负责"执行与交叉验证"，中间用 renderer + orchestrator 做"强约束聚合"。**
