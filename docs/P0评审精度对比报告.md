# 蜂群评审精度对比：P0 type 枚举修复前后



> 日期：2026-08-31   范围：cspm_agent / loop-dev / deepseek-harness-master 三项目

> 方法：同一份 agent 输出，分别用 修复前 renderer（render-report.cjs.p9bak，12项封闭 enum）与 修复后 renderer（P0，开放字符串 + 26项推荐列表）渲染，量化精度差。

> 结论先行：修复前 other 桶饱和率 40%（6/15）且对高频真实类型 strict 模式直接阻断（exit=3）；修复后类型可精确归类、未知类型独立入待复核不降级不丢弃，门禁判定无回归。



---



## 一、问题定性：精度损失是真实存在的根因

agent-output-schema 与 renderer 修复前的 type 为 12 项封闭 enum：

masked_bug / missing_test / god_file / hardcoded_secret / config_drift / missing_validation / design_flaw / performance_issue / doc_gap / compliance_gap / observability_gap / other



真实评审中出现的高频类型 monkey_patch（运行时替换库函数）、missing_coverage（无测试覆盖配置）、dup_code（复制粘贴重复代码）、missing_config / hardcoded_config（配置债）不在枚举内，只能被降级映射或挤压。



## 二、证据 A：三个真实项目 fixture 的 type 分布（现状基线）



| 类型 | 次数 |

|------|-----|

| `other` | 6 |

| `design_flaw` | 4 |

| `missing_test` | 1 |

| `missing_validation` | 1 |

| `god_file` | 1 |

| `hardcoded_secret` | 1 |

| `doc_gap` | 1 |



- 全量 15 条发现中，other 占 6 条（40%），是所有类型里最高的桶。

- 这正是修复前丢失信息的直接体现：架构评审的价值在按类型统计高发维度、沉淀基线、金样按类型回归对比，而 other 饱和意味着这些发现无法被按类型聚合，后续分析全部失真。

- 按项目分布：

  - `eval-cspm-agent.json`：other=1；细分={'missing_test': 1, 'missing_validation': 1, 'god_file': 1, 'design_flaw': 2, 'hardcoded_secret': 1, 'other': 1}

  - `eval-loop-dev.json`：other=2；细分={'design_flaw': 1, 'other': 2}

  - `eval-deepseek-harness.json`：other=3；细分={'other': 3, 'design_flaw': 1, 'doc_gap': 1}



## 三、证据 B：对照实验（同一份输入，两版 renderer）

把 deepseek-harness 中原本被打进 other 的发现，按真实语义标注为高频类型后，跑两版 renderer：



| 真实语义类型 | 修复前（p9bak）strict | 修复前 lenient | 修复后（P0） |

|-------------|---------------------|----------------|--------------|

| monkey_patch | 抛错 exit=3 | 仅扁平告警，不归类不统计 | 识别为已知推荐类型，纳入统计 |

| missing_coverage | 抛错 exit=3 | 仅扁平告警，不归类不统计 | 识别为已知推荐类型，纳入统计 |

| hardcoded_config | 抛错 exit=3 | 仅扁平告警，不归类不统计 | 识别为已知推荐类型，纳入统计 |

| totally_custom_zzz（完全未知） | 抛错 exit=3 | 仅扁平告警 | 保留原值，进入 type_unknown 待复核区 |



### 关键行为差异（实测）

1. 修复前 strict：对任何不在 12 项内的 type，validateAgentOutput 报 type invalid 错误，renderer 整体 throw，报告无法产出，精度为 0。

2. 修复前 lenient：仅把 type invalid 追加到扁平 warnings 列表，无 type_unknown 独立归集、不进待复核、不按类型统计；发现以原始 type 裸出现在正文，无法按类型聚合。

3. 修复后 P0：monkey_patch / missing_coverage / hardcoded_config 已在推荐列表，被精确识别并纳入统计桶；完全未知类型 totally_custom_zzz 不抛错、保留原始值、独立归入待复核项下的类型未知（type_unknown）区，带完整证据行，供人工归类。



## 四、精度差量化



| 指标 | 修复前 | 修复后 | 改善 |

|------|--------|--------|------|

| 高频类型（monkey_patch/missing_coverage/hardcoded_config/dup_code 等）识别 | 无法识别（抛错/降级） | 精确入桶 | 100% |

| 未知类型处理 | strict 阻断 / lenient 扁平告警 | 保留 + type_unknown 待复核 | 可追溯 |

| 是否污染统计桶（design_flaw/other） | 是（被迫降级挤压） | 否 | 消除 |

| 报告可产出性（strict） | 存在未知 type 即抛错 | 始终产出 exit=0 | 稳定 |

| 门禁判定一致性（三项目） | 与修复后一致（无回归） | 一致 | 无回归 |

## 六、一句话结论

P0 修复消除了真实存在的精度根因：三项目真实评审中 other 桶饱和率高达 40%，修复前高频类型（monkey_patch/missing_coverage/hardcoded_config）在 strict 模式下直接阻断评审（exit=3）、lenient 下只扁平告警不归类；修复后这些类型被精确识别入统计桶，完全未知的类型独立进 type_unknown 待复核区不降级不丢弃，且门禁判定零回归。
