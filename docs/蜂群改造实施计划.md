# architect-skills 蜂群改造实施计划（场景 B：方案评估与矫正）

> 计划日期：2026-08-31（重写，取代上一版草案）
> 上游依据：`docs/蜂群模式改造提案.md`（技术方向）+ P9 评估（取舍收敛）+ 使用场景二轮澄清
> 状态：待评审
> **本版定位（钉死）**：架构师 skill 的本质使用场景是**场景 B（全面评审）**——蜂群 + architect-skills 结合，对用户提出的**改造/项目方案**进行**评估与矫正**的开发路径。本计划即围绕这条主线重写。

---

## 〇、两句话概括

**要做什么**：把 architect-skills 从"单代理深度评估"演进为"蜂群编排评估"，评审对象从"代码现状"升级为"用户提出的改造方案"，并产出一条评估→矫正→闭环的落地路径。

**不做什么**：不让场景 A（单原子设计咨询）被蜂群化；不预建无实证的规模设施（DAG 并行、独立仲裁代理）。

## 一、定位与边界（场景 A / B 分界）

| | 场景 A：单原子设计咨询（保留，不蜂群化） | 场景 B：方案评审与矫正（本计划主线） |
|---|---|---|
| 触发 | "安全设计怎么做""API 这样设计行不行" | "帮我评估/矫正这个改造方案""从开发到上线" |
| 对象 | 单一设计维度的决策 | 用户提出的整体改造/项目方案 |
| 执行 | 单 atom 直接回答（原则+决策树+反模式） | 蜂群多 agent 并行评审 + 聚合 |
| 交付 | 设计建议（给选择给取舍） | 评估报告 + **可落地矫正项** + 闭环跟踪 |
| 是否进蜂群 | 否 | 是 |

> 硬约束：场景 B 的契约化/编排改造，**不得回流污染场景 A 的轻量咨询体验**。场景 A 仍读完整 guide，不走 contract 填表。

## 二、三条改造主线（围绕场景 B）

### 主线 1：输入即方案（评审对象升级）

当前 architect-skills 全面分析吃的是"代码 Intake 建图"。场景 B 下，蜂群的第一输入是**用户提出的改造/项目方案**（可能含：目标 / 现状差异 / 改动范围 / 迁移路径 / 兼容策略 / 验收标准）。

**应新增 scheme 以外的一层"方案评审表"**，让每个维 agent 在评代码之前先评方案本身：

```json
{
  "proposal": {
    "target": "描述",
    "gap": "现状→目标差异",
    "scope": "改动文件/边界",
    "migration": "迁移路径/阶段",
    "compat": "兼容与回滚策略",
    "acceptance": "可运行验收标准"
  },
  "per_dimension_checks": [
    {"dim","question","risk_if_missing"}
  ]
}
```

**为何必要**：改造型方案最常见的坑不在代码里，而在"方案没定义清楚"——目标不量化、缺回滚、缺兼容、验收不可运行。蜂群若只评代码，会在错误的方案地基上浪费评审。

**联动**：renderer 聚合时新增"方案完整性"区块，未填 `target/gap/scope/migration/compat/acceptance` 任一项 → 该方案标记 `PROPOSAL_INCOMPLETE`，先补方案再评代码（对应风险分级 unknown 兜底，见主线 2）。

---

### 主线 2：契约分层 + 编排 + 聚合器（骨架）

采纳提案改造 1/2/3/4，作为场景 B 的主干。三个关键落点：

1. **契约层（改造 1）**：atom 拆「契约 + guide」。契约给蜂群代理"查什么、输出什么（含 confidence）"；guide 保留判断力。**门禁：agent 输出必须引用 guide 具体原则/反模式 ID，契约只是索引。** 做法：先只拆 `architect-security` 单 atom 试点，验证判断力不退化，再铺开。

2. **编排层（改造 2）**：`swarm-orchestrator.md` 定义任务分发、冲突仲裁、证据合并协议。在证据合并**之前**强制插入 `MISSING_AGENT` 缺失告警（loop-dev 实证 Halley `completed:null`）——任何 agent 失联或返 `completed:null` → 该维 `unknown`，整方案不得判"通过"，降级"待补评"。仲裁沿用四条：安全一票否决 > 证据优先 > 耦合度优先 > `NEED_HUMAN_DECISION` 兜底。

3. **聚合器（改造 3）**：render-report.cjs 从 60 行占位符升级为强约束聚合器：证据去重、冲突检测标 `CONFLICT`、风险升级、**空 section 拒绝（缺必填 throw，不落半成品）**、confidence=unknown 单独进「待复核」。保留 `--lenient` 兼容开关，避免单代理/现存金样一次全红。

**风险分级扩展（改造 4）**：risk-grading-scheme 增加 `high/medium/low/unknown` 置信度列；`unknown` 必须显式标记不跳过。同时新增 `reference/agent-output-schema.json` 统一 agent 输出字段。

---

### 主线 3：评估→矫正闭环（场景 B 的核心增量）

> 用户点名的是"评估**和矫正**"。评审不是打完分就结束，必须产出可落地矫正项并跟踪到方案修订。

1. **矫正建议结构化**：每个 critical/high 发现必须带矫正四件套——
   - **改什么**（方案修改点 / 代码修改点，含 file:line 级证据）
   - **怎么改**（具体方案或范式）
   - **怎么验证**（可运行命令 + 通过条件，GREEN-first）
   - **怎么回滚**（失败时的撤退路径）
   这复用现有 report 第 ⑤ 节 C/H 详述格式，但把"矫正"从"建议"升级为"强制字段"。

2. **迭代跟踪（改造 8 上调为第二批主线）**：新增评估工单 —— `发现ID → 矫正项 → 验证 → 关闭证据`。下一轮蜂群复评只关注上一轮未关闭项 + 本次变更新增项。数据结构沿用提案 §三 那张表（发现ID/代理/维度/风险/状态/验证代理/关闭证据）。**先用手工 markdown 表沉淀两轮，出现"撑不住"证据再脚本化。**

3. **闭环验收**：同一方案修订后复评，critical 数应单调递减；每个 closed 项都必须有"关闭证据"（验证命令通过），无证据的不得 closed。

| 变更 | 说明 |

## 五、全局验收标准

1. 失联不再静默：agent 失联 → `MISSING_AGENT` + `unknown`，方案不判通过。
2. 半成品不再生成：缺必填 → renderer throw。
3. 方案完整性受控：缺 target/gap/backfill 任一项 → `PROPOSAL_INCOMPLETE`。
4. 矫正可落地：每个 critical/high 都带"改什么/怎么改/验证/回滚"四件套。
5. 闭环可跟踪：无关闭证据不得 closed；复评 critical 单调递减。
6. 判断力不退化：security 单维评审"原则引用数 + 行级证据密度"契约化后 ≥ 改造前。
7. 场景 A 不受污染：单原子设计咨询仍走完整 guide，不强制走 contract 填表。

## 六、风险与开放问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| 契约化后 agent 只填表丢判断力 | 评审深度退化 | 单 atom 试点先验 + guide 门禁强制引用原则 ID |
| 方案评审表过严误伤小方案 | 简单改造被挡 | `PROPOSAL_INCOMPLETE` 仅作提示，不自动阻塞小改动（分级处理） |
| renderer 强约束误伤单代理 | 现存金样全红 | `--lenient` 兼容开关 + 先跑金样回归对照 |
| 缺失告警误报 | 健康 agent 被误判失联 | 超时窗口可配，`MISSING_AGENT` 可人工复核降级 |
| 矫正字段被填成空话 | 闭环失真 | 无"验证命令"的矫正项直接 `unknown` 不可 closed |

> 📌 场景 B 主线即以蜂群 + architect-skills 评估并矫正用户的改造/项目方案：第一批做缺失告警+renderer硬聚合+置信度标记，第二批接入方案评审表靠编排契约、矫正四件套、工单闭环与金样回归，single security atom 试点契约分层，DAG 与独立仲裁延后/否决，场景 A 设计咨询侧保持不变。
