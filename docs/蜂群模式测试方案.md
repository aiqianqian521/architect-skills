> 版本：v1.0

## 一、测试目标

| 目标ID | 目标描述 | 验收标准 |
|--------|----------|----------|
| T1 | 所有 atom 的 contract.json 合法且完整 | `validate-contracts.mjs` 零报错通过 |
| T2 | renderer 能正确聚合多 agent 输出 | 输入 mock agent 输出 → 输出完整 L2 报告，无空 section |
| T3 | renderer 能检测并标记跨维度冲突 | 输入矛盾建议 → 报告显式标记 CONFLICT |
| T4 | renderer 拒绝不合规输入（空字段、非法值） | 输入缺必填字段 → throw Error，不生成半成品报告 |
| T5 | risk-grading-scheme 置信度机制生效 | 所有 agent 输出必须含 confidence 字段，否则 renderer 标为 unknown |
| T6 | regression-guard 能检测口径漂移 | 同一项目两次评估，同条件定级不同 → 触发漂移告警 |
| T7 | swarm-orchestrator 规则可被 agent 解析执行 | 真实蜂群评估后，agent 输出符合 agent-output-schema.json |
| T8 | 端到端：改造后蜂群评估质量不低于改造前 | loop-dev 项目重评，不遗漏 M5/M1/M2/M4/Q1/Q2 等已知发现 |

## 二、测试分层

### L1：单元测试（我独立完成）

**测试工具**：Node.js 原生 assert + 本地 mock 数据

| 测试项 | 输入 | 预期输出 | 测试脚本 |
|--------|------|----------|----------|
| validate-contracts | 15 个 atom 的 contract.json | 零报错 / 具体错误列表 | `scripts/validate-contracts.mjs` |
| renderer-聚合 | 2-3 个 mock agent JSON | 完整五段报告 | `tests/renderer-aggregate.test.mjs` |
| renderer-冲突检测 | 2 个 agent 对同一文件矛盾建议 | CONFLICT 标记 + 仲裁建议 | `tests/renderer-conflict.test.mjs` |
| renderer-空字段拒绝 | 缺必填字段的 agent 输出 | Error: "Missing required field: evidence" | `tests/renderer-reject.test.mjs` |
| renderer-置信度过滤 | 含 unknown confidence 的发现 | 归入「待复核」章节 | `tests/renderer-confidence.test.mjs` |
| regression-guard | 两次评估的 golden sample | 漂移告警列表 | `tests/regression-guard.test.mjs` |

**Mock 数据规范**：
```json
{
  "agent": "Bacon",
  "dimension": "test",
  "findings": [
    {
      "id": "M5",
      "type": "masked_bug",
      "evidence": "test_close_event_records_probe_success_count: threshold-restore logic masked",
      "file_line": "event_store_test.go:312",
      "risk_level": "medium",
      "confidence": "high",
      "next_step": "add explicit probe success count assertion"
    }
  ]
}
```

### L2：集成测试（你配合执行）

**测试工具**：真实 agent 环境 + 项目靶子

| 测试项 | 方法 | 验收标准 |
|--------|------|----------|
| agent 输出合规性 | 跑一轮蜂群评估，收集原始 JSON | 所有输出符合 `agent-output-schema.json`，无字段缺失 |
| renderer 端到端 | 把真实 agent 输出喂给 renderer | 生成完整 L2 报告，与人工审阅结论一致 |
| 冲突检测准确率 | 检查 renderer 标记的 CONFLICT | 人工复核：真冲突是否被 catch，假冲突是否被误报 |
| 置信度合理性 | 检查各 agent 的 confidence 分布 | high 应该有直接证据支撑，unknown 应该确实无法评估 |
| 金样回归 | 用 regression-guard 对比新旧评估 | 已知发现（M5 等）不漏，定级不漂移 |

**项目靶子建议**：
- loop-dev（已知发现基线完整）
- lvfs_git_aegis（当前活跃项目，有容器化改造等真实需求）

### L3：混沌测试（你配合执行）

**测试工具**：故障注入 + 观察系统行为

| 故障场景 | 注入方法 | 预期行为 |
|----------|----------|----------|
| agent 超时 | 模拟 Halley `completed:null` | orchestrator 标记该维度为 unknown，不阻塞其他维度 |
| agent 输出 malformed JSON | 截断 JSON 或插入非法字符 | renderer throw Error，给出具体文件名和错误位置 |
| agent 结论矛盾 | 强制 design 和 test 给出相反建议 | renderer 标记 CONFLICT，按仲裁规则处理 |
| agent 遗漏必填字段 | 删除 confidence 或 evidence | renderer 拒绝聚合，提示缺失字段 |
| 跨项目定级漂移 | 同一条件上次 high 本次 medium | regression-guard 触发漂移告警 |

## 四、测试通过标准

| 级别 | 通过条件 | 不通过处理 |
|------|----------|------------|
| L1 单元测试 | 所有 assert 通过，覆盖率 > 80% | 阻塞，修复后再进 L2 |
| L2 集成测试 | 与人工审阅结论一致性 > 90% | 记录偏差 case，进入第三轮调优 |
| L3 混沌测试 | 所有故障场景系统不崩溃，有明确错误信息 | 记录未处理异常，修复后再测 |
